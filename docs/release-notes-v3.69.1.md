# v3.69.1 发布说明 — 补丁：修复在线接收时界面卡死

**发布日期:** 2026-11-27

## 问题

「追踪」页在线接收 CAN 数据时，界面点不动、数据刷新极慢，但任务管理器里 CPU 和内存都正常，标题栏也不显示「未响应」。断开通道后立即恢复。

现象随接收时长加重（越跑越卡），与「上限」行数设置无关——把上限从 5000 改成 100 仍然卡。

## 根因

两处叠加：

1. **每帧一次集合通知。** `AppendBatchCore` 逐帧 `Entries.Add`，达到上限后逐帧 `Entries.RemoveAt(0)`。500 fps 下每 200 ms 一批约 100 帧，稳态产生约 200 次 `CollectionChanged`。DataGrid 每次都在 UI 线程同步做视图维护（行映射、索引协调、可见区重算），虚拟化只能减少实际创建的视觉行，**无法把这两百次通知合并**。

2. **投递优先级压过输入与绘制。** 数据摄入经 `Dispatcher.InvokeAsync` 以默认 `DispatcherPriority.Normal(9)` 投递，而 WPF 的 `Input(5)` 与 `Render(7)` **优先级更低**。持续的数据任务把点击与重绘长期饿死——这就是「点不动、画面不刷新，但消息泵仍在转」的原因，也解释了为什么标题栏不显示「未响应」。

两者形成正反馈：单批处理超过 200 ms → 等待期间接收通道继续积累 → 下一批更大 → 通知更多 → 更慢。

## 修复

- **批量替换集合。** 新增 `BatchObservableCollection<T>.ApplyBatch(removeCount, toAppend)`：头部批量移除 + 尾部批量追加，**只发一条 `CollectionChanged(Reset)`**。每批通知数从约 200 次降为 1 次，与帧率解耦。
- **降低投递优先级。** `AppendBatchAsync` 与 `RunOnUiPost`（所有 ~30 Hz 数据刷新的统一入口：信号表、DBC 解码回填、J1939 事件、统计）从 `Normal` 降到 `Background(4)`。输入与渲染始终先得到处理；接收侧有 10 000 条有界通道兜底，晚一批无副作用。
- **统计面板限流。** 底部「报文统计」原每批（5 Hz）重建：对全部不同 CAN ID 排序 + `Clear` + 最多 20 次 `Add`。现在限流到 2 Hz，且当 Top-20 榜单未变时**只原地更新数值，零集合通知**。

## 顺带修复

- **单批超限裁错行。** `MaxRows` 小于单批帧数时（例如上限 2 却一次来 3 帧），原逻辑会保留错误的行；现在从合并序列头部正确裁掉。由既有测试 `MaxRows_Trims_Oldest_On_Next_Batch` 覆盖。

## 升级说明

无配置迁移、无 API 变更。行为差异仅在通知频率与调度优先级，用户可见语义（FIFO 保留窗口、视图层过滤、导出、自动滚动）保持不变。
