# v3.70.0 发布说明 — 小版本：结论可定位 + 刷写配对修复

**发布日期:** 2026-11-27

## 问题一：结论和明细里的编号指不到任何数据

结论栏的 `#N` 是分析器内部位置，但事务表没有序号列——用户数到第 N 行也无从下手，一筛选更是彻底错位；校验失败明细与传输警告里的「证据 #N」是**帧级**序号，而该页面根本没有帧列表。

## 修复一：编号可对、可点、可跳

- 事务对象新增报告序号 `Index`（分析阶段一次定死），结论文案 `#N`、事务表首列、导出 Markdown/CSV 的 `transaction_index` 全部同源，筛选不重编号。
- 结论行的 `#N` 是可点徽标：点一下选中该事务并滚动到表里那一行；目标被筛选隐藏时先清筛选（选中了看不见等于没定位）。
- 校验失败明细显示「事务 #N · 证据 #M」，整行可点定位；右栏「原始证据」补入失败响应帧（校验没过的响应不会挂到事务上，原来点过去是空的）。
- 传输警告行给出首帧时间 / 通道 / CAN ID；找不到归属的孤立帧在状态栏如实说明，不假装跳转。
- 右栏证据行首改为「证据 #N」，与报表明细同一词表。

## 问题二：245.644 s 之后 TransferData 全部误报「未闭合」

真实刷写日志（634,548 帧，扩展帧 `18DAD1F1/18DAF1D1`）：

- 214.309 s 的最后一块 `TransferData`（块号 `0x82`）ECU 只回了流控，从未回 `76 82`；随后 `0x37` 被 NRC `0x24` 拒绝，复位后重新下载。
- 配对是「同 SID、最早打开」：这条永远没回的请求一直排在队首，之后每条同 SID 响应都先与它比对，块号对不上 → 记成「回显校验失败」。
- 结果：全文件 327 条假校验失败；新一轮从块 `01` 开始的 TransferData 条条「未闭合」，而它们其实都收到了 `76 01…`。

## 修复二：按回显证据配对

- 同 SID 多条在途请求时，正响应交给**回显对得上**的那条；一个都对不上才退回最早一条，沿用原有的失败计数。
- 新的 `RequestDownload` 发起了新一轮下载：上一轮未闭合的 `0x36/0x37` 作废，原因落在结构化字段 `SupersededBy` 上；结论走专用归因（「本请求不可能再收到响应」），不再给「延长记录时间」这类永远无效的建议。
- 作废块的迟到响应按回显还给原请求并闭合，不再记成「重复最终响应」，也不算到新请求头上。

## 验证

- 真实日志复验：校验失败 327 → 0；事务 1254 正响应 / 5 负响应 / 1 未闭合（仅 214.309 s 那条真的没回的 `0x82`，并注明被后续下载作废）；245.644 s 之后 TransferData 全部闭合。
- 定向测试：Core UDS 分析 292 项、App UDS 120 项全部通过（新增编号一致性、筛选下定位、证据反查、作废归因、迟到响应归属等用例）。
