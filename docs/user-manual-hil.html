1. HIL 测试框架概述

1.1 什么是 HIL 测试

HIL（Hardware-in-the-Loop，硬件在环）测试框架是 PeakCan Host 的核心测试能力之一，用于在真实 CAN 总线上编写、执行和验证自动化测试用例。

与纯软件模拟测试不同，HIL 测试直接操作 PCAN-USB FD 硬件，向真实 ECU 发送 CAN 帧并验证其响应。这使得 HIL 测试特别适合：

  • ECU 集成测试：验证多个 ECU 之间的交互行为
  • 回归测试：固件更新后快速验证已有功能未被破坏
  • 故障注入测试：模拟异常总线条件验证 ECU 容错能力
  • UDS 诊断流程验证：自动化执行诊断会话/读写/刷写等流程
  • CI/CD 集成：在持续集成管道中自动运行 CAN 总线测试

2. 快速入门：5 分钟跑通第一个测试

以下示例演示一个完整的 HIL 测试流程：发送一个 CAN 帧，然后验证 ECU 的响应。

步骤 1：准备硬件

  1. 插上 PCAN-USB FD
  2. 启动 PeakCan Host
  3. Probe → Connect（连接到目标 ECU 所在的总线）
  4. 加载 DBC 文件（File ▸ Open DBC...）

步骤 2：打开 HIL 面板

菜单 View ▸ HIL 打开 HIL 测试面板。

步骤 3：创建测试用例

在 HIL 面板中，点击 新建测试用例，输入以下内容：

测试用例 1名称:   发送诊断请求并验证响应

描述:   发送 0x10 03（编程会话请求），等待 ECU 正响应

步骤:

  1. [SendFrame]   发送 CAN ID 0x7DF，数据 10 03

  2. [Delay]       等待 100ms

  3. [ExpectFrame] 期望 CAN ID 0x7E8，数据前缀 50 03

  4. [AssertNrc]   无 NRC 返回

步骤 4：运行测试

点击 Run 按钮，观察执行进度：

用例名称 发送诊断请求并验证响应 步骤 1 ✅ SendFrame 0x7DF → 10 03 步骤 2 ✅ Delay 100ms 步骤 3 ✅ ExpectFrame 0x7E8 ← 50 03 （匹配） 步骤 4 ✅ AssertNrc — 无 NRC 结果 ✅ 通过（4/4 步骤全部通过，耗时 210ms）
提示：首次运行前请确认 DBC 文件中包含消息 ID 0x7DF 和 0x7E8 的定义，或者确保 HIL 面板中已正确配置目标 CAN ID。

3. 测试用例模型

3.1 TestCase 数据结构

一个测试用例包含以下字段：

字段类型说明
Idstring唯一标识符（如 "TC-CAN-001"）
Namestring人类可读的测试用例名称
Descriptionstring详细描述测试目的
PreConditionsstring?前置条件说明（当前为文档性）
StepsIReadOnlyList<TestCaseStep>测试步骤列表（按顺序执行）
PostConditionsstring?后置条件说明（当前为文档性）
TagsIReadOnlyList<string>标签，用于分类筛选（如 ["smoke", "uds"]）
TimeoutMsint用例超时时间（毫秒），0 表示不限制
CaseFixtureKeysIReadOnlyList<string>?用例级 fixture 键列表
设计原则：TestCase 是纯数据模型（record），可序列化为 JSON/YAML 持久化存储。

3.2 测试步骤类型

框架支持 11 种测试步骤，每种对应一个 TestCaseStepKind：

步骤类型标识功能
SendFrameTestCaseStepKind.SendFrame向总线发送一帧 CAN 消息
SendSequenceTestCaseStepKind.SendSequence发送预定义的帧序列
ExpectFrameTestCaseStepKind.ExpectFrame等待期望的 CAN 帧到达
WaitForSignalTestCaseStepKind.WaitForSignal等待信号达到指定值
AssertSignalTestCaseStepKind.AssertSignal断言信号当前值在容差内
AssertRangeTestCaseStepKind.AssertRange断言信号值在指定范围内
AssertDtcTestCaseStepKind.AssertDtc断言 ECU 的 DTC 状态
AssertNrcTestCaseStepKind.AssertNrc断言 UDS 负响应码
AssertResponseTimeTestCaseStepKind.AssertResponseTime断言 ECU 响应时间在阈值内
DelayTestCaseStepKind.Delay等待指定时间（毫秒）
CommentTestCaseStepKind.Comment注释，不计入执行统计

3.3 创建测试用例

HIL 面板支持两种方式创建测试用例：

方式 1：UI 创建（推荐初学者）

  1. 在 HIL 面板点击 新建测试用例
  2. 填写用例名称、描述、标签
  3. 点击 添加步骤，选择步骤类型并填写参数
  4. 拖拽步骤可调整顺序
  5. 点击 保存

方式 2：编码创建（C# 代码）

C# 代码using PeakCan.Host.Core.HIL;

var testCase = new TestCase(

    Id: "TC-CAN-001",

    Name: "发送诊断请求并验证响应",

    Description: "验证 ECU 对 0x10 03 诊断会话请求的响应",

    PreConditions: "ECU 已上电，总线连接正常",

    Steps: new TestCaseStep[]

    {

        TestCaseStep.Create(new SendFrameParams(0x7DF, [0x10, 0x03]),

            label: "发送编程会话请求"),

        TestCaseStep.Create(new DelayParams(100),

            label: "等待 ECU 处理"),

        TestCaseStep.Create(new ExpectFrameParams(0x7E8, [0x50, 0x03]),

            label: "验证正响应"),

        TestCaseStep.Create(new AssertNrcParams(),

            label: "确认无负响应"),

    },

    PostConditions: "ECU 保持在当前会话",

    Tags: new[] { "smoke", "uds", "diagnostic" },

    TimeoutMs: 5000

);

4. 测试步骤详解与示例

4.1 SendFrame — 发送帧

向 CAN 总线发送一帧消息。这是最基础的步骤，用于触发 ECU 的响应。

参数类型说明
CanIduintCAN ID（11 位或 29 位）
Databyte[]数据字节
IsExtendedbool是否使用 29 位扩展帧格式
IsFdbool是否使用 CAN-FD 帧格式
示例 — 发送 UDS 诊断请求// 发送 0x22 F1 90（ReadDataByIdentifier — VIN）

TestCaseStep.Create(new SendFrameParams(

    CanId: 0x7DF,

    Data:  [0x22, 0xF1, 0x90],

    IsExtended: false,

    IsFd: false

), label: "发送 VIN 读取请求");



// 发送 0x2E F1 90 + 数据（WriteDataByIdentifier — 写 VIN）

TestCaseStep.Create(new SendFrameParams(

    CanId: 0x7DF,

    Data:  [0x2E, 0xF1, 0x90, 0x31, 0x48, 0x47, 0x43, 0x4D],

    IsExtended: false,

    IsFd: false

), label: "发送 VIN 写入请求");

4.2 SendSequence — 发送序列

按顺序发送一组预定义的帧，每帧之间可指定间隔。

参数类型说明
FramesIReadOnlyList<CanFrame>要发送的帧序列
IntervalMsint帧间间隔（毫秒）
示例 — 发送 UDS 会话切换序列// 发送 Default → Extended → Programming 三个会话请求

TestCaseStep.Create(new SendSequenceParams(

    Frames: new CanFrame[]

    {

        new(0x7DF, [0x10, 0x01]),  // Default 会话

        new(0x7DF, [0x10, 0x02]),  // Extended 会话

        new(0x7DF, [0x10, 0x03]),  // Programming 会话

    },

    IntervalMs: 50

), label: "遍历三种诊断会话");

4.3 ExpectFrame — 等待期望帧

等待总线上出现与指定模式匹配的 CAN 帧。支持数据掩码匹配。

参数类型说明
ExpectedIdCanId期望的 CAN ID
DataMaskbyte[]?数据掩码（null 表示不检查数据）
TimeoutMsint超时时间（毫秒），默认 1000
示例 1 — 等待 UDS 正响应// 发送 0x10 03 后等待 0x50 03 正响应

// 步骤 1: SendFrame(0x7DF, [0x10, 0x03])

// 步骤 2: ExpectFrame(0x7E8, [0x50, 0x03])

TestCaseStep.Create(new ExpectFrameParams(

    ExpectedId: 0x7E8,

    DataMask:   [0x50, 0x03],  // 匹配 SID+SubFunction

    TimeoutMs:  1000

), label: "等待编程会话正响应");



示例 2 — 只等待 ID，不关心数据TestCaseStep.Create(new ExpectFrameParams(

    ExpectedId: 0x7E8,

    DataMask:   null,  // 任何数据都匹配

    TimeoutMs:  500

), label: "等待 ECU 返回任何响应");

4.4 WaitForSignal — 等待信号值

等待 DBC 解码后的信号达到指定值（在容差范围内）。需先加载 DBC 文件。

参数类型说明
SignalNamestring信号名，格式 "MessageName.SignalName"
ExpectedValuedouble期望的物理值
Tolerancedouble容差范围
TimeoutMsint超时时间（毫秒），默认 5000
示例 — 等待发动机转速达到目标值// 发动机管理系统发送转速信号后，等待转速达到 2500 rpm

TestCaseStep.Create(new WaitForSignalParams(

    SignalName:    "Engine_State.Engine_RPM",

    ExpectedValue: 2500.0,

    Tolerance:     50.0,      // ±50 rpm 容差

    TimeoutMs:     10000      // 最多等 10 秒

), label: "等待发动机转速达到 2500 rpm");

底层实现通过 AssertionPrimitives.WaitForSignalAsync：

HIL 源代码 — WaitForSignalAsync 实现邏輯public async Task<AssertionResult> WaitForSignalAsync(

    string name, double expected, double tolerance, CancellationToken ct)

{

    var matchTcs = new TaskCompletionSource<bool>();

    using var sub = _ctx.SubscribeDecodedFrames(frame =>

    {

        var val = _ctx.GetSignalValue(name, maxAgeMs: 5000);

        if (val is { } v && Math.Abs(v - expected) <= tolerance)

            matchTcs.TrySetResult(true);

    });

    // 等待匹配或超时/取消

    var cancelTask = Task.Delay(Timeout.Infinite, ct);

    var winner = await Task.WhenAny(matchTcs.Task, cancelTask);

    // ... 返回 Pass 或 Fail

}

4.5 AssertSignal — 断言信号值

立即检查信号当前值是否在容差范围内。与 WaitForSignal 不同，不等待——只检查当前值。

参数类型说明
SignalNamestring信号名，格式 "MessageName.SignalName"
ExpectedValuedouble期望的物理值
Tolerancedouble容差范围
示例 — 验证冷却液温度// 在 ECU 发送冷却液温度后，断言温度在 90°C ± 5°C

TestCaseStep.Create(new AssertSignalParams(

    SignalName:    "Engine_State.Coolant_Temp",

    ExpectedValue: 90.0,

    Tolerance:     5.0

), label: "冷却液温度应在 85-95°C");

4.6 AssertRange — 断言信号范围

断言信号当前值在指定的最小/最大范围内。

参数类型说明
SignalNamestring信号名
Mindouble最小值（含）
Maxdouble最大值（含）
示例 — 验证电池电压范围// 整车正常工作时，电池电压应在 11.0V - 14.5V

TestCaseStep.Create(new AssertRangeParams(

    SignalName: "BMS_Status.Battery_Voltage",

    Min:        11.0,

    Max:        14.5

), label: "电池电压应在 11.0V ~ 14.5V 范围内");

4.7 AssertDtc — 断言 DTC

读取 ECU 的 DTC（诊断故障码）并断言其状态。

参数类型说明
DtcCodeuintDTC 代码（3 字节）
AssertPresentbooltrue = 断言 DTC 存在，false = 断言 DTC 不存在
TimeoutMsint超时时间（毫秒）
示例 1 — 验证故障码已设置// 在故障注入后，验证 P0123（油门踏板位置传感器故障）已设置

TestCaseStep.Create(new AssertDtcParams(

    DtcCode:      0x050123,  // P0123

    AssertPresent: true,

    TimeoutMs:    5000

), label: "验证 DTC P0123 已设置");



示例 2 — 清除后验证故障码已清除// 清除故障码后，确认不再存在

TestCaseStep.Create(new SendFrameParams(0x7DF, [0x14, 0xFF, 0xFF, 0xFF]),

    label: "清除所有 DTC"),

TestCaseStep.Create(new AssertDtcParams(

    DtcCode:      0x050123,

    AssertPresent: false,

    TimeoutMs:    5000

), label: "验证 DTC P0123 已清除");

4.8 AssertNrc — 断言 NRC

断言 UDS 负响应码（NRC）符合预期。用于验证 ECU 正确拒绝非法请求。

参数类型说明
ExpectedNrcbyte?期望的 NRC 值（null 表示期望无 NRC）
TimeoutMsint超时时间（毫秒）
示例 1 — 安全访问拒绝测试// 发送错误的密钥，期望 NRC 0x35 (invalidKey)

TestCaseStep.Create(new SendFrameParams(0x7DF, [0x27, 0x05, 0x00, 0x00]),

    label: "发送错误的安全访问密钥"),

TestCaseStep.Create(new AssertNrcParams(

    ExpectedNrc: 0x35,      // invalidKey

    TimeoutMs:   1000

), label: "验证收到 invalidKey 拒绝");



示例 2 — 期望成功（无 NRC）// 发送有效请求，期望无负响应

TestCaseStep.Create(new AssertNrcParams(

    ExpectedNrc: null,      // 无 NRC

    TimeoutMs:   1000

), label: "ECU 应正常响应，无 NRC");

4.9 AssertResponseTime — 断言响应时间

断言 ECU 对请求的响应时间在指定阈值内。用于验证实时性要求。

参数类型说明
RequestIduint请求帧的 CAN ID
ResponseIduint响应帧的 CAN ID
MaxResponseTimeMsint最大允许响应时间（毫秒）
示例 — 验证 UDS 诊断响应时间// 发送 0x22 F1 90（读 VIN），ECU 应在 100ms 内响应

TestCaseStep.Create(new SendFrameParams(0x7DF, [0x22, 0xF1, 0x90]),

    label: "发送读 VIN 请求"),

TestCaseStep.Create(new AssertResponseTimeParams(

    RequestId:        0x7DF,

    ResponseId:       0x7E8,

    MaxResponseTimeMs: 100

), label: "VIN 读取响应应在 100ms 内");

4.10 Delay — 延时等待

在步骤之间插入等待时间，用于等待 ECU 处理或总线稳定。

参数类型说明
DelayMsint等待毫秒数
示例 — 常用延时场景// 发送请求后等待 50ms

TestCaseStep.Create(new DelayParams(50), label: "等待 50ms");



// 总线初始化后等待 2s 让 ECU 启动

TestCaseStep.Create(new DelayParams(2000), label: "等待 ECU 初始化完成");

4.11 Comment — 注释

注释步骤不在执行时产生任何操作，也不计入执行统计。用于在步骤列表中插入说明文字。

示例 — 插入注释TestCaseStep.Create(new CommentParams("=== 以下测试 UDS 安全访问 ==="),

    label: "注释：安全访问测试阶段"),

    label: "请求种子"),

TestCaseStep.Create(new CommentParams("期望 ECU 返回 0x67 01 + 4 字节种子"),

    label: "注释：预期行为说明");

5. 测试套件与执行引擎

5.1 TestSuite 数据结构

测试套件是测试用例的集合，包含共享配置和 fixture：

字段类型说明
Namestring套件名称

5.2 三阶段执行引擎 (Stage A/B/C)

测试套件通过 TestSuiteEngine 执行，分为三个阶段：

Stage A
Setup → Stage B
Execute → Stage C
Teardown
阶段说明失败处理
Stage A — Setup 初始化所有 fixture（硬件连接、DBC 加载、UDS 会话建立等）。如果 fixture 初始化失败，整个套件被标记为 SetupFailure。 Stage A 失败 → 跳过 Stage B，直接进入 Stage C
Stage B — Execute 按顺序执行每个测试用例。每个用例内部按步骤顺序执行，任何步骤失败导致该用例失败。 根据 StopOnFirstFailure 配置决定是否继续执行后续用例
Stage C — Teardown 清理所有 fixture（断开硬件、释放资源）。即使 Stage B 失败也强制执行。 Teardown 失败记录到 SetupFailures 列表，不影响测试结果
TestSuiteEngine 执行流程（伪代码）async Task<TestSuiteResult> RunAsync(TestSuite suite, IAssertionContext ctx, CancellationToken ct)

{

    var setupFailures = new List<string>();

    // Stage A: Setup

    try { await SetupFixtures(suite, ct); }

    catch (Exception ex) { setupFailures.Add(ex.Message); return EarlyExit(suite, setupFailures); }



    // Stage B: Execute

    var results = new List<TestCaseResult>();

    foreach (var @case in suite.Cases)

    {

        if (ct.IsCancellationRequested) break;

        var result = await RunTestCase(@case, ctx, ct);

        results.Add(result);

        if (!result.Passed && suite.Config.StopOnFirstFailure) break;

    }



    // Stage C: Teardown

    try { await TeardownFixtures(suite, ct); }

    catch (Exception ex) { setupFailures.Add($"Teardown: {ex.Message}"); }



    return Aggregate(suite, results, setupFailures);

}

6. DiffEngine — 差异比较引擎

DiffEngine 用于比较两个帧序列，支持三种粒度。特别适合固件升级前后的回归测试。

6.1 帧级比较 (Frame Granularity)

按位置逐帧比较。每个帧的 ID、DLC、数据逐一对比。

帧级比较var engine = new DiffEngine();  // 无需 DBC

var result = engine.Diff(goldenFrames, actualFrames, new DiffConfig(

    Granularity: DiffGranularity.Frame,       // 帧级

    Alignment:   AlignStrategy.Timestamp,      // 按时间戳对齐

    Tolerance:   new ToleranceSpec(0, 0)       // 零容差（精确匹配）

));



// 输出:

//   Matched: 142 帧

//   Modified: 3 帧

//   Added: 1 帧

//   Removed: 0 帧

6.2 事件级比较 (Event Granularity)

基于"事件"（如 DID 读取、DTC 设置等高级语义）进行比较，而非逐帧。

事件级比较var result = engine.Diff(goldenFrames, actualFrames, new DiffConfig(

    Granularity: DiffGranularity.Event,

    Alignment:   AlignStrategy.NearestNeighbor,  // 最近邻对齐

    Tolerance:   new ToleranceSpec(0.1, 0.05),   // 绝对容差 0.1 + 相对容差 5%

    NeighborWindowMs: 200                        // 200ms 窗口内找最近邻

));

6.3 信号级比较 (Signal Granularity)

需要 DBC 文件。按 DBC 解码后的信号物理值进行比较，而非原始字节。这是最语义化的比较方式。

信号级比较// 需要 DBC 查找服务

var engine = new DiffEngine(dbcLookup);  // 传入 IDbcLookup

var result = engine.Diff(goldenFrames, actualFrames, new DiffConfig(

    Granularity: DiffGranularity.Signal,      // 信号级

    Alignment:   AlignStrategy.Timestamp,

    Tolerance:   new ToleranceSpec(5.0, 0.1)  // 绝对 5.0 + 相对 10%

));



// 逐信号输出:

//   Engine_RPM: matched=120, modified=2, added=0, removed=0

//   Vehicle_Speed: matched=98, modified=0, added=0, removed=0

//   Coolant_Temp: matched=50, modified=1, added=0, removed=0

6.4 比较配置

配置项可选值说明
GranularityFrame / Event / Signal比较粒度
AlignmentTimestamp / NearestNeighbor / Index帧对齐策略
ToleranceToleranceSpec(double absolute, double relative)容差配置（绝对 + 相对）
NeighborWindowMsint（默认 100ms）最近邻对齐的搜索窗口
容差配置示例// 严格容差：精确匹配

new ToleranceSpec(AbsoluteTolerance: 0, RelativeTolerance: 0)



// 宽松容差：允许 ±1.0 绝对误差或 ±5% 相对误差

new ToleranceSpec(AbsoluteTolerance: 1.0, RelativeTolerance: 0.05)



// 只检查相对容差

new ToleranceSpec(AbsoluteTolerance: 0, RelativeTolerance: 0.1)

8. TraceDrivenChannel — 基于录制数据的回放测试

TraceDrivenChannel 是 HIL 框架中的特殊通道，基于已录制的 .asc 或 .blf 文件驱动测试，不需要真实硬件即可运行 HIL 测试。

这在以下场景非常有用：

  • 离线开发：在无硬件环境下调试测试用例
  • 回归测试：用历史录制数据验证新版本 ECU 行为
  • CI 环境：在无硬件的 CI 服务器上运行测试（使用录制数据）
使用 TraceDrivenChannel（伪代码）// 创建 TraceDrivenChannel，加载录制文件

var channel = new TraceDrivenChannel("recordings/engine_startup.asc");



// 注册到 HIL 上下文

var ctx = new HilAssertionContext(channel, dbcLookup);



// 运行测试 — 回放录制帧，测试引擎检查帧序列

var result = await runner.RunAsync(suite, ctx, ct);

// 结果:

//   用例 "发动机启动时序验证": ✅ 通过

//   用例 "怠速转速范围":      ✅ 通过

注意：TraceDrivenChannel 是只读回放通道。SendFrame 等写入操作在此通道上会返回失败结果。如需写入总线，请使用真实硬件通道。
