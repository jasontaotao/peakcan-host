1. HIL 测试框架概述

1.1 什么是 HIL 测试

HIL（Hardware-in-the-Loop，硬件在环）测试框架是 PeakCan Host 的核心测试能力之一，用于在真实 CAN 总线上编写、执行和验证自动化测试用例。

与纯软件模拟测试不同，HIL 测试直接操作 PCAN-USB FD 硬件，向真实 ECU 发送 CAN 帧并验证其响应。这使得 HIL 测试特别适合：

  • ECU 集成测试：验证多个 ECU 之间的交互行为
  • 回归测试：固件更新后快速验证已有功能未被破坏
  • 故障注入测试：模拟异常总线条件验证 ECU 容错能力
  • UDS 诊断流程验证：自动化执行诊断会话/读写/刷写等流程
  • CI/CD 集成：在持续集成管道中自动运行 CAN 总线测试

2. 快速入门：5 分钟跑通第一个测试

以下示例演示一个完整的 HIL 测试流程：发送一个 CAN 帧，然后验证 ECU 的响应。

步骤 1：准备硬件

  1. 插上 PCAN-USB FD
  2. 启动 PeakCan Host
  3. Probe → Connect（连接到目标 ECU 所在的总线）
  4. 加载 DBC 文件（File ▸ Open DBC...）

步骤 2：打开 HIL 面板

菜单 View ▸ HIL 打开 HIL 测试面板。

步骤 3：创建测试用例

在 HIL 面板中，点击 新建测试用例，输入以下内容：

测试用例 1名称:   发送诊断请求并验证响应

描述:   发送 0x10 03（编程会话请求），等待 ECU 正响应

步骤:

  1. [SendFrame]   发送 CAN ID 0x7DF，数据 10 03

  2. [Delay]       等待 100ms

  3. [ExpectFrame] 期望 CAN ID 0x7E8，数据前缀 50 03

  4. [AssertNrc]   无 NRC 返回

步骤 4：运行测试

点击 Run 按钮，观察执行进度：

用例名称 发送诊断请求并验证响应 步骤 1 ✅ SendFrame 0x7DF → 10 03 步骤 2 ✅ Delay 100ms 步骤 3 ✅ ExpectFrame 0x7E8 ← 50 03 （匹配） 步骤 4 ✅ AssertNrc — 无 NRC 结果 ✅ 通过（4/4 步骤全部通过，耗时 210ms）
提示：首次运行前请确认 DBC 文件中包含消息 ID 0x7DF 和 0x7E8 的定义，或者确保 HIL 面板中已正确配置目标 CAN ID。

用一个具体例子看区别：

假设你的测试用例是：发送 0x10 03（编程会话请求），然后等待 0x50 03 响应

模式谁会收到你的请求？谁会给你响应？需要什么？
Hardware CAN 总线上的真实 ECU（通过 PCAN-USB 发送出去） 真实 ECU 通过 CAN 总线返回响应 PCAN-USB 硬件 + 真实 ECU（已上电）
Offline (Trace) 没人收到——你的请求被忽略（只读回放） 响应来自之前录制的 .asc/.blf 文件 只需要一个录制文件，不需要硬件
VirtualEcu PCAN-USB 发出去，但接线是环回或接在同一台 PC 的另一个通道上 本机运行的 ECU 模拟器脚本（JSON 定义的状态机）自动响应 PCAN-USB 硬件 + ECU 脚本 JSON，不需要真实 ECU
Matrix 同上，但可以同时发给多个虚拟 ECU 多个 ECU 模拟器各自响应，模拟多 ECU 总线环境 PCAN-USB + 多个 ECU 脚本 JSON

所以你应该这样选：

通道选择操作：

  1. 在"通道"下拉框中，选择已连接的 PCAN 硬件通道（USB1、USB2 等）
  2. 如果 PCAN 硬件未连接，下拉框为空，提示"未检测到硬件"
  3. 在 Offline 模式下，点击 Trace 路径旁的 [浏览...] 按钮，选择 .asc 或 .blf 文件
  4. 选中的文件路径显示在文本框中，支持拖拽文件到输入框

Faults 和 Analyze 复选框：

在模式配置行右侧有两个复选框，分别是 Faults 和 Analyze：

复选框绑定的属性作用
Faults EnableFaultInjection 故障注入总开关。勾选后，运行测试时启用 CAN 帧故障注入。
故障注入规则由测试套件或 ECU 脚本定义（Drop/Delay/Corrupt/Duplicate），

不勾选时不会自动分析，但可以手动点击 [Analyze] 按钮触发。
关联功能：§8d LLM 分析

简单记：Faults = 让总线出故障来测试 ECU 容错能力；Analyze = 让 AI 帮你分析为什么测试失败了。

5.2 三阶段执行引擎 (Stage A/B/C)

测试套件通过 TestSuiteEngine 执行，分为三个阶段：

图 2 — TestSuiteEngine 三阶段执行管线。Stage A 失败则跳过 Stage B，Stage C 总是执行。
阶段说明失败处理
Stage A — Setup 初始化所有 fixture（硬件连接、DBC 加载、UDS 会话建立等）。如果 fixture 初始化失败，整个套件被标记为 SetupFailure。 Stage A 失败 → 跳过 Stage B，直接进入 Stage C
Stage B — Execute 按顺序执行每个测试用例。每个用例内部按步骤顺序执行，任何步骤失败导致该用例失败。 根据 StopOnFirstFailure 配置决定是否继续执行后续用例
Stage C — Teardown 清理所有 fixture（断开硬件、释放资源）。即使 Stage B 失败也强制执行。 Teardown 失败记录到 SetupFailures 列表，不影响测试结果
TestSuiteEngine 执行流程（伪代码）async Task<TestSuiteResult> RunAsync(TestSuite suite, IAssertionContext ctx, CancellationToken ct)

{

    var setupFailures = new List<string>();

    // Stage A: Setup

    try { await SetupFixtures(suite, ct); }

    catch (Exception ex) { setupFailures.Add(ex.Message); return EarlyExit(suite, setupFailures); }



    // Stage B: Execute

    var results = new List<TestCaseResult>();

    foreach (var @case in suite.Cases)

    {

        if (ct.IsCancellationRequested) break;

        var result = await RunTestCase(@case, ctx, ct);

        results.Add(result);

        if (!result.Passed && suite.Config.StopOnFirstFailure) break;

    }



    // Stage C: Teardown

    try { await TeardownFixtures(suite, ct); }

    catch (Exception ex) { setupFailures.Add($"Teardown: {ex.Message}"); }



    return Aggregate(suite, results, setupFailures);

}

8a. ECU 独立模拟器 — 无测试套件的仿真模式 已实现

8a.1 概述

ECU 独立模拟器（Standalone Simulator）是 Phase 5 Sprint 13 引入的功能，允许在没有测试套件的情况下，在真实 PCAN 通道上运行一个虚拟 ECU。它加载一个 ECU 脚本 JSON 文件，定义状态机和响应规则，然后自动响应来自总线的 UDS 请求。

与测试套件模式不同，独立模拟器：

  • 不需要 JSON 测试套件文件 — 直接加载 ECU 脚本
  • 自动 ISO-TP 响应 — 基于状态机自动回复，无需手动编写步骤
  • 阻塞运行 — 连接成功后持续运行，直到 Ctrl+C 退出
  • 支持 stateless 和 stateful 两种模式

典型应用场景：

  • 开发调试：在测试工具开发过程中替代真实 ECU
  • 回归测试：用模拟 ECU 验证测试工具本身的功能
  • 演示展示：无需连接真实 ECU 即可演示 HIL 测试流程

8a.2 命令行用法

基本用法# 启动 ECU 模拟器，阻塞运行
peakcan-hil --dbc vehicle.dbc \
            --ecu bms_simulator.json \
            --hw USB1 \
            --simulate
# 输出: Simulating ECU 'BMS_Simulator' on USB1. Press Ctrl+C to exit.
参数说明
--dbcDBC 文件路径（用于日志中的信号解码）
--ecuECU 模拟器脚本 JSON 路径
--hw硬件通道名（USB1..USB16）
--uds-reqUDS 请求 CAN ID（默认 0x7DF，ECU 视角）
--uds-respUDS 响应 CAN ID（默认 0x7E8）

8b. 故障注入 — 模拟总线异常 已实现

说明：FaultRule 模型、IFaultInjectionContext 接口、4 种故障类型（Drop/Delay/Corrupt/Duplicate）均已实现。UI 中需勾选 "Faults" 复选框启用。

8b.1 概述

故障注入（Fault Injection）是 Phase 3/4 引入的能力，允许在测试执行期间模拟 CAN 总线异常，验证 ECU 的容错能力和故障响应行为。

故障注入通过 IFaultInjectionContext 接口管理，支持在发送路径和接收路径上注入故障。

8b.2 故障类型

故障类型FaultType说明
丢帧Drop丢弃匹配的 CAN 帧（支持概率性丢帧）
延迟Delay延迟指定毫秒数后发送
损坏Corrupt对指定字节位置进行 XOR 掩码损坏
重复Duplicate将帧发送两次（模拟总线重复帧）

每个 FaultRule 包含以下配置：

参数说明
Type故障类型（Drop / Delay / Corrupt / Duplicate）
TargetCanId目标 CAN ID（null = 匹配所有帧）

DelayMs延迟毫秒数（仅 Delay 类型）
CorruptByteIndices要损坏的字节位置（仅 Corrupt 类型）
CorruptXorMask损坏 XOR 掩码（默认 0xFF，仅 Corrupt 类型）

热重载机制：

  1. GeneratorPluginManager 使用 FileSystemWatcher 监控插件目录的 *.dll 变化
  2. 检测到文件创建/修改后，经 300ms 去抖延迟触发重载
  3. 每个 DLL 加载到独立的 AssemblyLoadContext（collectible），不锁定源文件
  4. 加载失败（如缺少接口实现）的 DLL 被跳过，不影响正在运行的生成器
  5. 重载成功后触发 GeneratorsChanged 事件，EcuStateMachine 自动替换生效
