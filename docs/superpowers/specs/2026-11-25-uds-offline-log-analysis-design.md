## 1. 背景与问题

当前 UDS 窗口已经支持在线会话、安全访问、DID、例程、DTC 和刷写，但现场日志带回后，仍缺少一条只读分析路径：

- ISO-TP 多帧需要人工拼接，连续帧和流控帧干扰定位。
- 请求、正响应、负响应和连续 `NRC 0x78` 分散在原始帧中，难以还原一次完整事务。
- 未看到响应、记录缺帧、地址配置错误和 ECU 未回复容易被混为一谈。
- DID 响应已经具备 ODX 解码基础，但只服务于在线读取结果。
- 在线 `IsoTpLayer` 会过滤单一响应 ID，并在收到首帧后主动发送流控，不能直接用于只读离线分析。

本需求新增一条独立的数据解释路径：读取已有 ASC/BLF，重组诊断消息，形成请求—响应事务，并把结论与原始证据放在一起。它不是在线诊断脚本、回放器或 DBC 信号分析。

## 2. 目标与非目标

### 2.1 目标

1. 未连接硬件、未加载 DBC 或未加载 ODX 时，仍能分析 ASC/BLF 中采用 normal addressing 的 classic CAN UDS 物理寻址流量。
2. 同时重组请求和响应方向的单帧与多帧消息，保留每条原始帧证据。
3. 正确归并连续 `0x78`，区分直接成功、负响应、延迟成功、未闭合、归属歧义、重复最终响应和响应校验失败噪声。
4. 解释通用 SID/NRC、DID、例程名称及 `0x10` 正响应中的 P2/P2*。
5. 区分首次响应耗时与事务总耗时，并标明时序参数来源。
6. 列表、详情、导出和 AI 提示词使用同一份报告快照。
7. 离线分析本身不连接硬件、不发送 CAN；AI Handoff 不自动调用 LLM，只有用户在现有 AI 面板手动发送后才走 Provider。
8. 支持取消和部分报告，禁止用未完成阶段的数据伪造完整结论。

### 2.2 非目标

首版不包含：

- ~~功能寻址~~、多 ECU 并行分析、CAN FD ISO-TP、DoIP。
  <br/>**2026-11-27 更新：功能寻址已支持**（`UdsOfflineAddress.FunctionalId`），
  见 [2026-11-26-uds-offline-diagnosis-depth-design.md](2026-11-26-uds-offline-diagnosis-depth-design.md) §8.5。
  多 ECU 并行分析仍不支持——一份报告只描述一个请求/响应对。
- 扩展/混合 UDS 寻址；首版仅支持 normal addressing。本文“扩展帧”仅指 29 位 CAN ID。
- 大日志流式分析基础设施改造。
- DTC 快照、扩展数据和完整 DTC 语义深读。
- 在线诊断、日志回放、HIL 脚本或 ECU 自动控制。
- 自动根因判断或自动 AI 发送；用户手动发送后的 Provider 网络与计费沿用现有聊天设置。
- 对非诊断帧做内容分析或来源归因（并行诊断源、另一个 tester）；首版只按 §7.4 分类计数与标记，不做裁决。
- 将诊断事务接入 TraceViewer 采样图；本功能不依赖 DBC。
- 修复现有在线 UDS 缺陷，包括在线 P2* 单位、DTC 请求格式或刷写块序号校验。它们需要独立缺陷与验收范围；离线只读校验（§8.5）不属于此类修复。

## 3. 已确认决策

| 决策 | 结论 | 原因 |
|---|---|---|
| D1 | 入口放在现有 `UdsWindow` 的“日志分析”页签 | 与 UDS 语义和 ODX 配置相邻，但不混入 TraceViewer 的 DBC 图表 |
| D2 | 新增纯离线分析器，不复用在线 `UdsClient` / `IsoTpLayer` | 在线层包含单一响应过滤、流控发送、真实定时器和在途请求状态 |
| D3 | 首版复用全量 `AscParser` / `BlfParser` | 保持时间归一化与排序口径一致，避免扩大为流式基础设施改造 |
| D4 | 沿用现有 200 MB 文件上限 | 与现有 `ReplayOptions` 边界一致；超限必须显式报错 |
| D5 | 一次分析一个 `(Channel, RequestId, ResponseId, IsExtended)` normal addressing 物理地址组合 | 防止跨通道、跨 ECU 或标准/扩展 ID 误配 |
| D6 | CAN ID 决定请求/响应角色，日志 Tx/Rx 只作证据 | 不同记录源的方向标记可缺失或含义不同 |
| D7 | P2 超阈值只标记，不关闭事务 | 迟到响应仍是日志中可观察到的有效证据 |
| D8 | P2 原始值单位为 ms；P2* 原始值乘 10 ms | 符合 UDS 时间参数编码，避免复制在线现有换算问题 |
| D9 | ODX 在分析开始时取快照 | 分析期间共享数据库变化不得改写当前报告 |
| D10 | 显式加载 ODX 仍走现有共享入口 | 不新增第二套 ODX 导入器；离线不等于暗中修改在线配置 |
| D11 | 换文件或重新分析使旧报告失效 | 防止旧日志结论显示在新文件上下文中 |
| D12 | 导出与 AI 读取当前面板同一报告快照 | 避免列表、导出和 AI 各看一份不同数据 |
| D13 | AI 复用追踪查看器现有对话面板，通过 Handoff 预填脱敏提示词 | 打开/唤回同一窗口并保留聊天机制；不新增聊天 UI、不自动发送，手动发送才走 Provider |
| D14 | 在线已发现缺陷不夹带修复 | 本需求不改变在线验收口径和运行行为 |
| D15 | 对地址不匹配/无法成帧的帧只分类计数，不分析、不裁决 | 日志无法区分“另一个诊断源”和“本人重试”（D6 方向标记不可信）；§8.5 的响应一致性校验属于防误判，不是根因裁决 |
| D16 | 地址匹配但无法成帧的输入进噪声桶并保留证据 | 让“报告少算帧”可被用户核对，而不是静默丢弃 |
| D17 | SID 未知但 ISO-TP 成帧合法的输入仍建事务并标 `UnknownService` | 不能因服务表不全丢掉真实 OEM 服务；标记而非丢弃 |
| D18 | 响应闭合前做最小长度与回显校验；不符则进噪声桶、不判确定成功 | 刷写期间响应 ID 上的周期帧可能以 `0x76` 开头，只靠 SID 配对会静默误判成功 |
| D19 | 诊断定义快照 = 分析开始时 `DidDatabase.All` / `RoutineDatabase.All` 的当时内容，来源为内置默认，以及用户 JSON 或已导入 ODX 之一 | 无 ODX 不是分析前置条件；现有 ODX 导入会重置用户 JSON 条目，二者不并存 |
| D20 | 离线页保留共享“加载 ODX…”入口，加载只影响下一次分析 | 复用现有导入，不新增第二套；当前报告必须保持不可变 |
| D21 | `OdxLoaded` 与用户 JSON 加载状态由 App 层随分析请求传入；`DidDatabase` 新增只读加载状态属性 | 现有数据库只暴露 `All`，加载结果只写日志；不指定权威来源，报告字段只能靠猜 |

## 4. 现状证据与复用边界

### 4.1 可直接复用

- `Core/Replay/ReplayFrame.cs`：提供相对时间、原始 ID、DLC、数据、`Flags`（含 CAN FD 标记）、扩展帧标记、通道和可空方向。
- `Core/Replay/AscParser.cs` 与 `BlfParser.cs`：提供全量 ASC/BLF 解析、格式错误和取消边界。
- `Core/Replay/ReplayOptions.cs`：现有默认文件上限为 200 MB。
- `Core/Uds/UdsException.cs`：已有标准 NRC 枚举可参考，但离线解释必须另行覆盖 `0x78` 和未知值回退。
- `peakcan-hil-core/Uds/Odx/DidValueDecoder.cs`：可把 DID 数据解码为 ASCII、UNICODE2、整数、浮点、枚举和原始 hex。
- `DidDatabase.All` / `RoutineDatabase.All`：在分析开始时生成只读定义快照。快照来源是当时数据库的实际内容：内置默认，加上用户 JSON（`uds-dids.json` / `uds-routines.json`）或已导入 ODX 之一（现有 ODX 导入先 `Clear()` 再 `AddRange()`，会重置用户 JSON 条目，二者不并存）。`DidDatabase` 的 5 个内置 DID（`0xF190`、`0xF187`、`0xF18A`、`0xF191`、`0xF184`）在无 ODX 时仍提供名称与期望长度，可做标识和长度校验；字段表（`DidDefinition.Fields`）按设计由 ODX 导入填充（用户 JSON 若带 `fields` 也会被反序列化），字段级解码缺失时回退原始 hex。`RoutineDatabase` 无内置默认，无用户 JSON 时为空。`DidDatabase` 需新增只读加载状态（如 `UserJsonLoadStatus`：未配置 / 文件缺失 / 加载成功 / 解析失败），`RoutineDatabase` 同口径；`OdxLoaded` 由 App 层在最近一次 `OdxImportResult` 成功时置位。
- NM 的纯分析器、部分报告、报告导出和提示词模式作为结构参考；UDS 分析不塞进 NM 或 TraceViewer，只复用追踪查看器已有 AI 对话面板。

### 4.2 只能复用规则，不能复用状态机

`Core/Uds/IsoTp/IsoTpLayer/ReceiveFlow.cs` 的在线行为包括：

- `ProcessFrame` 只接受配置的一个 `ResponseId`。
- 收到 First Frame 后调用 `SendFlowControl()`。
- 使用 N_Cr 看门狗和单份接收缓冲区。
- 完成消息通过在线事件交付。

因此，离线分析只复用 classic CAN PCI 编解码规则和已有测试经验，新增无发送、无墙钟定时器、按数据流隔离状态的离线重组器。

### 4.3 共享 ODX 的边界

`OdxImportService.ImportAsync` 会清空并重建共享 DID/例程/DTC 数据库，并可能更新刷写配置。离线分析器不得调用它来维持只读快照。

只有用户在界面显式选择“加载 ODX”时，才执行现有共享导入命令。每次离线分析固定当时的定义集合；导入后的新定义只影响下一次重新分析。

## 5. 总体架构

```text
ASC / BLF 文件
      |
      v
UdsOfflineTraceLoader  (App：文件对话框、IO、解析、200 MB 限制、取消)
      |
      v
IReadOnlyList<ReplayFrame> + 地址配置 + ODX 快照
      |
      v
UdsOfflineAnalyzer     (Core：纯分析，无 IO / UI / 硬件)
      |
      +--> UdsFrameClassifier
      |         按地址切分：匹配诊断帧 / 非诊断帧 / 噪声帧 / 未支持输入
      |         （响应校验失败帧在配对后回填噪声桶）
      |
      +--> OfflineIsoTpReassembler
      |         请求与响应分别按 Channel + ID + IsExtended 重组
      |
      +--> UdsTransactionBuilder
      |         SID 配对、0x78 归并、孤立响应、歧义与未闭合
      |
      +--> UdsSessionTimingTracker
      |         0x10 正响应、P2 / P2* 来源及单位换算
      |
      +--> UdsServiceInterpreter
                通用 SID/NRC、DID、例程、原始值回退
      |
      v
UdsOfflineReport       (不可变报告快照)
      |
      +--> UdsLogAnalysisViewModel --> 列表 / 详情 / 原始证据
      +--> UdsOfflineReportWriter --> Markdown / CSV
      +--> UdsOfflineAiPromptBuilder
                |
                v
           ITraceViewerChatHandoffService
                |
                v
           现有 TraceViewer AI 对话（预填，不自动发送）
```

### 5.1 分层要求

- Core 分析层不引用 WPF、文件对话框、`UdsClient`、硬件通道、发送服务或 `ILlmProvider`。
- App 层负责文件 IO、ODX 共享导入、后台任务、界面状态、导出对话框、提示词生成、AI Handoff 和草稿保护。
- 报告一旦生成即不可变；筛选只改变可见行，不重算或改写报告。
- 首版不做跨文件报告缓存；当前报告只保留在 UDS ViewModel 生命周期内，不持久化到会话文件。

## 6. 核心数据契约

以下为设计契约，不要求逐字采用相同语法，但语义不得丢失。

### 6.1 分析请求

`UdsOfflineAnalysisRequest` 至少包含：

- `ReportId`：本次分析唯一标识。
- `SourceId` / `SourcePath`：文件身份与原始来源；脱敏输出不得泄露完整路径。
- `Frames`：本次解析得到的不可变帧集合。
- `Address`：`Channel`、`RequestId`、`ResponseId`、`IsExtended`。
- `Diagnostics`：DID 与例程定义快照、定义来源（报告级聚合：内置默认；用户 JSON 是否加载成功；是否已导入 ODX）、`OdxLoaded` 标记和快照标识。`OdxLoaded` 取 App 层最近一次成功 ODX 导入，用户 JSON 状态取 `DidDatabase` / `RoutineDatabase` 的只读加载状态；两者由 `UdsLogAnalysisViewModel` 在发起分析时随请求传入，不从 `All` 反推。
- `EngineVersion`：离线分析器版本，供报告追溯。

### 6.2 原始证据

`UdsFrameEvidence` 至少包含：

- 证据序号：稳定排序后的位置序号（从 0 开始）；排序稳定，不重排相同时间戳的帧，也不改写解析器给出的原始顺序。
- 时间戳、通道、原始 CAN ID、标准/扩展标记。
- 日志原始方向：`TX`、`RX` 或 `Unknown`。
- 最终分类桶（配对完成后回填）：匹配诊断帧、非诊断帧、噪声帧或未支持输入（§7.4）；噪声帧附带原因。
- ISO-TP 帧类型、原始数据和 DLC。

证据引用使用证据序号，不伪造 ASC 行号或 BLF 字节偏移。原始 `ReplayFrame` 可通过序号回取，详情只展开选中事务的证据，不渲染整份日志。

### 6.3 重组 PDU

`UdsOfflinePdu` 至少包含：

- 完整 UDS payload 和方向角色。
- 首帧与末帧时间、首末证据序号。
- 单帧/多帧、关联流控和连续帧证据。
- 完整/不完整状态及传输警告。

多帧 PDU 的时间范围必须同时保留首帧和末帧，不能只留一个时间点。

### 6.4 事务

`UdsOfflineTransaction` 至少包含：

- 请求 PDU、按时间排列的响应 PDU 和全部证据引用。
- 请求 SID、服务名称、DID/例程等可选对象标识。
- `FinalKind`：`Positive`、`Negative`、`None`。
- `PendingCount`、最终 NRC、孤立/歧义标记。
- 首次响应耗时、事务总耗时、时序评估和时序来源。
- ODX 解码字段；未解码时保留原始值和原因。
- 结论、不可知项和下一步检查提示。

界面状态由这些字段组合得出，不另建一套容易相互矛盾的“成功/失败”布尔值。

### 6.5 报告

`UdsOfflineReport` 至少包含：

- 请求中的文件、地址、诊断定义来源与 `OdxLoaded` 标记、分析器版本。
- 日志时间范围、输入帧数、匹配诊断帧数、非诊断帧数、噪声帧数和未支持输入计数；各项必须满足 §7.4 的闭合等式。
- 非诊断帧按 CAN ID 聚合（Top-N、计数与首末证据序号），不逐帧渲染。
- 事务、孤立响应、歧义响应、重复最终响应、响应校验失败计数、传输警告和不可知项。
- `IsPartial` 及部分完成原因。
- 已完成阶段标识；未执行阶段使用空集合，不填充假数据。

### 6.6 噪声与非诊断帧

`UdsNoiseSummary` 至少包含：

- 非诊断帧总数，以及按 CAN ID 聚合的 Top-N（ID、扩展标记、计数、首末证据序号）。
- 未支持输入总数及原因分类（CAN FD 等非 classic CAN 帧、其它超出首版范围的输入）。
- 匹配地址但无法成帧或无法归属的输入：计数、原始证据序号和原因（PCI 非法、DLC 不足、连续帧序号错误、无在途 PDU 的连续帧）。
- 响应一致性校验不通过：按 `ResponseValidationFailed` 计入噪声帧数，记录候选事务、证据序号和未通过项。
- 重复最终响应：按 `DuplicateFinalResponse` 单独列出（所属事务、证据序号），仍计入匹配诊断帧数，不重复计入噪声帧数。
- 分类计数必须与 §7.4 的闭合等式一致；Top-N 被截断时必须显式标注“聚合已截断”及完整 ID 数。

噪声汇总只做分类与计数，不做内容解释或来源归因（§2.2）。

## 7. 帧选择与离线 ISO-TP 重组

### 7.1 稳定顺序

1. 保留解析器给出的原始序号（只用于稳定排序；证据序号按 §6.2 生成）。
2. 按时间戳稳定排序；时间相同则保持解析顺序。
3. 不修改调用方持有的原始帧集合。
4. 地址匹配必须同时比较通道、ID 数值和扩展帧标记。

### 7.2 请求与响应角色

- `RequestId` 数据流用于形成请求 PDU。
- `ResponseId` 数据流用于形成响应 PDU。
- `IsTransmit` 不参与角色路由，只保留为原始证据。
- 方向未知不会导致帧被丢弃。

### 7.3 重组规则

- 每个 `(Channel, Id, IsExtended)` 拥有独立重组状态。
- Single Frame 直接形成完整 PDU。
- First Frame 开始多帧 PDU；Consecutive Frame 按序号追加，序号到 `0xF` 后回绕到 `0x0`。
- Flow Control 是对应多帧传输的证据，不形成独立 UDS 请求或响应。
- 离线路径永远不调用发送回调，也不因收到 First Frame 生成新的流控帧。
- 不使用墙钟 N_Cr 定时器中止日志重组。序号错误、新 First Frame 覆盖或日志结束造成的不完整必须显式记录。
- DLC 不足或 PCI 非法时，只使受影响数据流产生警告，不终止其它独立数据流；无法成帧的帧同时计入噪声桶（§7.4）。
- classic CAN normal addressing 之外的输入进入未支持计数；不得把 CAN FD 数据按 classic CAN 规则强行拼接。

### 7.4 地址匹配后的帧分类

地址匹配（通道、ID 数值、扩展标记全等）只决定“是否进入本次分析的候选集”，不决定“是否是诊断流量”。每帧按以下顺序只落一个桶：

1. **非 classic CAN 帧**（解析器标记为 CAN FD 等） → 未支持输入。无论地址是否匹配，都不按 classic CAN 规则解释。
2. **地址不匹配** → 非诊断帧桶（按 CAN ID 聚合）。其他 ECU、其他 ID 的应用报文全部落在这一类。
3. **地址匹配但无法成帧或无法归属**（PCI 非法、DLC 不足、连续帧序号错误、无在途 PDU 的连续帧） → 噪声桶，记录原因与证据序号，不创建 PDU、不创建事务。
4. **地址匹配且成帧合法，但 SID 不在已知服务表** → 正常建事务并标记 `UnknownService`，按 §10.1 显示 `SID 0xNN`，不静默丢弃。
5. **其余** → 匹配诊断帧，进入重组与配对。

计数闭合等式（报告必须成立）：

```text
输入帧数 = 匹配诊断帧数 + 非诊断帧数 + 噪声帧数 + 未支持输入数
```

情况 3 的帧只计入噪声帧数；情况 4 仍计入匹配诊断帧数。序号错误只把出错帧计入噪声，已接收的 FF/CF 保留匹配诊断帧分类并关联到不完整 PDU；无在途 PDU 的连续帧整帧计入噪声。成帧合法的流控帧计入匹配诊断帧数，畸形 FC 按情况 3 进噪声桶；流控帧按 §6.3 不形成独立 PDU。§8.5 中响应一致性校验不通过的帧在配对完成后回填为噪声帧，从匹配诊断帧数移入噪声帧数；重复最终响应不移动，仍计入匹配诊断帧数。

## 8. 请求—响应事务配对

### 8.1 基本规则

- 请求 PDU 创建事务并记录请求 SID。
- 正响应必须满足 `responseSid = requestSid + 0x40`。
- 负响应必须满足 `0x7F + 原请求 SID + NRC`。
- `NRC 0x78` 只追加等待过程，不结束事务，也不创建新事务。
- 其他 NRC 和匹配正响应结束对应事务。
- 找不到匹配在途请求的响应进入孤立响应集合。

### 8.2 不同 SID 重叠

同一物理地址允许观察到不同 SID 的在途事务。响应按 SID 找到对应事务，不以“最近一次请求”替代 SID 校验。

### 8.3 相同 SID 重叠

若同一地址在前一个相同 SID 尚未闭合时再次出现相同请求：

1. 前一个事务标记为未闭合及重叠。
2. 新事务记录重叠关系。
3. 后续同 SID 响应进入歧义证据集合。
4. 该响应不得把任意一个重叠请求计为确定成功。

首版采用保守归属，不根据时间接近程度猜测真实归属。

### 8.4 未闭合与迟到响应

- P2 超阈值只添加时序标记，不从事务匹配集合中删除请求。
- 只要仍是唯一匹配的在途 SID，迟到响应仍可正常完成事务。
- 日志结束时仍无最终响应的事务标记为未闭合。
- 文案只能是“日志中未看到匹配响应”，不能写成“ECU 没有发送”。
- 记录过滤、地址配置、记录缺帧和 ECU 未回复均保留为可能性。

### 8.5 响应一致性校验

SID 配对（§8.1）是最低条件。为避免响应 ID 上的非诊断帧被当作最终响应，闭合前还须满足最小长度与回显校验：

| 请求服务 | 期望正响应 | 闭合前校验 |
|---|---|---|
| 0x10 | 0x50 | 长度 ≥ 6；sessionType 回显一致；P2/P2* 另见 §9.1 |
| 0x22 | 0x62 | 长度 ≥ 3；DID 回显一致 |
| 0x2E | 0x6E | 长度 ≥ 3；DID 回显一致 |
| 0x27 | 0x67 | 长度 ≥ 2；子功能回显一致（忽略 suppressPosRsp 位） |
| 0x31 | 0x71 | 长度 ≥ 4；例程 ID 回显一致 |
| 0x34 | 0x74 | 长度 ≥ 3；lengthFormatIdentifier 决定长度字段宽度，首版不展开 |
| 0x36 | 0x76 | 长度 ≥ 2；块序号回显一致（离线只读校验，不改变在线行为，§2.2） |
| 0x37 | 0x77 | 长度 ≥ 1 |
| 0x3E | 0x7E | 长度 ≥ 2；子功能回显一致（忽略 suppressPosRsp 位） |
| 0x7F | 负响应 | 长度 = 3 |

- 校验不通过 → 该响应按 `ResponseValidationFailed` 计入噪声桶，不参与配对、不计入首次响应耗时、不进孤立响应集合，证据关联候选事务；事务不被该帧闭合，若之后收到通过校验的响应仍可正常闭合，否则在日志结束时保持未闭合，并记录原因“收到疑似非本事务响应”。
- 校验通过但同一请求随后又收到第二个最终响应 → 第一个仍作为 `FinalKind`，第二个附加为该事务证据并设置 `DuplicateFinalResponse`；事务结论降级为“归属歧义”，不判确定成功，也不把第二个静默归入孤立响应。
- 不在表中的服务只做 SID 配对与最小长度（≥ 2）；无法校验的部分明确记为“未校验”，不冒充已校验。
- 上述规则只能降低同 ID 噪声的误判，不能区分来源；并行诊断源仍作为不可知项保留（§17）。

## 9. 会话时序与耗时

### 9.1 P2/P2* 来源

只有匹配当前地址的 `DiagnosticSessionControl` 正响应才能更新时序快照，并满足：

- 正响应 SID 与当前 `0x10` 请求匹配。
- 响应长度包含完整的 sessionType、P2 和 P2* 字段。
- sessionType 回显一致性由 §8.5 校验决定；只有校验通过的 `0x50` 才会进入本阶段并更新时序。
- P2 原始值为毫秒。
- P2* 原始值乘 10 ms 后得到毫秒。

判别示例：

```text
50 02 00 32 01 F4
             |  |  |
             |  |  +-- P2* low
             |  +----- P2* high = 0x01F4 = 500；500 × 10 ms = 5000 ms
             +-------- P2 = 0x0032 = 50 ms
```

新的时序只影响该正响应之后的同事务地址数据，不回写更早事务，也不改变在线 `UdsTimer`。

取得有效 `0x10` 正响应前，报告显示“未取得 ECU 时序”。不得把构造默认值 50/5000 ms 写成 ECU 已协商值。

### 9.2 两个耗时指标

- `首次响应耗时`：请求最后一帧时间 → 首个通过 §8.5 校验的响应首帧时间（含 `0x78`）。
- `事务总耗时`：请求首帧时间 → 最终响应最后一帧时间。
- 未闭合事务（`FinalKind=None`）不计算事务总耗时，显示“截至日志结束”并保留最后观测帧时间，不填 0 或伪造终值。

连续 `0x78` 的等待时间从事务经过中可读。P2* 评估以最近一次等待响应之后的下一次响应为依据，并保留实际时间和来源。

多帧传输时间属于事务总耗时的一部分，不得单独解释为 ECU 内部处理时间。

## 10. 服务与 ODX 解释

### 10.1 通用解释

- 对常见 UDS SID 提供服务名称；未知 SID 显示 `SID 0xNN` 并标记 `UnknownService`，不丢弃该事务。
- NRC 至少覆盖现有枚举及 `0x78 ResponsePending`。
- 未知名称或 OEM 范围值显示 hex，不抛出异常，不借用相近名称。
- 负响应证明 ECU 拒绝了该请求，不单独证明算法、种子、会话或软件根因。

### 10.2 DID

对匹配 `ReadDataByIdentifier` 的正响应：

1. 校验响应 DID 与请求 DID 一致。
2. 从本次分析开始时的诊断定义快照取得 `DidDefinition`；快照按当时数据库实际内容，可能含内置默认、用户 JSON 和已导入 ODX。
3. 去掉 SID 和 DID 后，将数据区交给 `DidValueDecoder`。
4. 无法解码时保留原始 hex，并按 §10.4 标注具体降级原因。
5. 当前报告继续使用开始分析时的定义，即使共享数据库随后被替换也不改变。

### 10.3 例程

RoutineControl 使用快照中的例程 ID 映射名称。未知例程保留 ID 和原始数据，不推断其内部条件。

### 10.4 无 ODX / 无定义时的行为

ODX 是可选输入，不是分析前置条件。没有 ODX 时：

- ISO-TP 重组、事务配对、`0x78`、P2/P2*、NRC、噪声分类全部照常。
- `DidDatabase` 的 5 个内置 DID 仍提供名称与期望长度（可标识、可做长度校验），但字段级解码需要字段表；无字段表时按 `NoFieldTable` 回退原始 hex。其余无定义的 DID 按 `NoOdx` / `OdxMissingDefinition` 回退。
- `RoutineDatabase` 无内置默认，无用户 JSON 时为空；例程保留 ID 和原始数据。
- 报告摘要标注 `OdxLoaded`；每处降级值旁标注具体原因。`OdxLoaded=false` 时文案为“未加载 ODX”，不得把空解码写成“数据异常”或“解析失败”。

降级原因至少区分：

| 原因 | 含义 |
|---|---|
| `NoOdx` | 本次分析未加载 ODX，且快照中没有该对象的其它来源定义（用户 JSON / 内置）；文案“未加载 ODX” |
| `OdxMissingDefinition` | 已加载 ODX，但快照中没有该对象定义（ODX、用户 JSON、内置都没有）；文案“ODX 未包含该定义” |
| `NoFieldTable` | 有定义，但没有字段表或字段表述不足以解码 |
| `PayloadTooShort` | 数据长度短于定义要求的长度 |
| `IncompleteData` | 多帧重组不完整或数据区不满足解码器要求 |

现有 ODX 导入行为是 `Clear()` 后再 `AddRange()`：`DidDatabase.Clear()` 回到内置默认、`RoutineDatabase.Clear()` 清空，因此导入 ODX 后用户 JSON 条目不再保留，快照来源最多是“内置 + 用户 JSON”或“内置 + ODX”。报告只记录实际采用的来源（报告级聚合），不逐条溯源，也不追溯条目覆盖顺序。

## 11. UDS 窗口与 ViewModel 设计

### 11.1 新增组件

- `UdsLogAnalysisViewModel`：文件、地址设置、分析/取消、报告、筛选、选中事务、状态和 AI Handoff 命令。
- `UdsLogAnalysisView`：离线页签内容，避免继续扩大现有 `UdsWindow.xaml`；不包含聊天界面或提示词预览区。
- `IUdsOfflineTraceLoader` / `UdsOfflineTraceLoader`：App 层文件与解析边界。
- `UdsOfflineReportWriter`：Markdown/CSV 纯文本生成。
- `UdsOfflineAiPromptBuilder`：从脱敏报告生成提示词，不持有聊天或 LLM 依赖。
- `ITraceViewerChatHandoffService`：打开/唤回现有追踪查看器并把提示词交给其 AI 对话，不持有 UDS 分析状态。

`UdsViewModel` 增加 `LogAnalysis` 子 ViewModel。其生命周期与现有 UDS 总 ViewModel 一致，但离线子 ViewModel 不得注入 `UdsClient`、硬件通道或发送服务。

### 11.2 页签显隐

在线 DID/例程/DTC/刷写页签保持原结构。

选中“日志分析”时：

- 隐藏默认/扩展/编程、安全访问、TesterPresent 和在线通信参数。
- 顶部会话条中的“加载 ODX…”入口保留，隐藏同一条中的会话、SecurityAccess 与 TesterPresent 控件。加载 ODX 走 D10 的共享导入，只影响下一次分析；加载完成后提示“重新分析以应用新定义”。刷写进行中沿用现有共享锁，不绕过。
- 隐藏共享在线输出日志，使用独立的离线状态条。
- 显示“打开 ASC/BLF”“重新分析”“导出报告”、诊断设置、事务列表和详情。
- 明确显示“离线只读；未连接硬件；发送 0 帧”。

若 `Flash.IsFlashing` 为真，刷写警告条在所有页签都保留。离线分析可以读取日志，但不得遮挡正在进行的在线刷写状态。

### 11.3 生命周期

- 切换页签不取消离线分析，返回时仍能看到同一任务。
- 选择新文件或点击重新分析：先取消旧任务，再使旧报告失效。
- 关闭窗口：通过 `Closing` 取消当前离线任务并丢弃部分报告；不在 `Closing` 中弹模态对话框或执行导出（会阻塞关窗）。部分报告只要求在窗口存续期间可用，关闭即失效，重开为新的空状态（§5.1）；不使用可能由模板/主题变化触发的 `Unloaded` 作为离线取消依据。
- 关闭后重开不得进入永久 disposed 状态。
- 本需求不改变现有 Session/Flash 的关闭语义。

### 11.4 界面状态

至少区分：

- 未选择文件。
- 文件读取中。
- 分析中，可取消。
- 完整报告。
- 部分报告。
- 完整/部分报告的附加标记：未加载 ODX（DID/例程按原始值显示，报告本身仍完整）。
- 读取/分析失败。
- 当前设置无匹配事务。
- 有报告但当前筛选无可见行。

“无匹配事务”和“筛选无可见行”不得共用同一句误导性空态。

## 12. 错误处理与证据边界

| 输入或异常 | 行为 |
|---|---|
| 文件不存在、不可读、格式错误、超过 200 MB | 显示具体错误，不产生成功报告 |
| 当前地址没有匹配帧 | 显示“当前设置下未识别到诊断事务”，并展示当前地址配置 |
| 地址不匹配的帧 | 进入非诊断帧桶，按 CAN ID 聚合计数，不参与事务，不逐帧渲染 |
| 非法 PCI、DLC 不足、序号错误、无在途 PDU 的连续帧 | 记录警告和证据，继续其它独立数据流；这些帧计入噪声桶（§7.4） |
| 未知 SID 但成帧合法 | 创建事务并标记 `UnknownService`，不静默丢弃 |
| 响应最小长度或回显校验不通过 | 按 `ResponseValidationFailed` 计入噪声桶，不计耗时、不进孤立集合；事务不被该帧闭合，之后收到通过校验的响应仍可正常闭合 |
| 同一请求收到多个最终响应 | 第二个作为证据附加并标 `DuplicateFinalResponse`，结论降级为归属歧义 |
| 多帧在日志结束时未完成 | 保留不完整 PDU 和原因，不生成虚假完整响应 |
| 无匹配响应 | 事务未闭合，保留所有观测可能性 |
| 孤立响应 | 单列计数和证据，不归入最近请求 |
| 相同 SID 重叠 | 标记归属歧义，不计算确定成功 |
| 缺少 ODX / 缺少定义 / 字段不完整 | 原始值回退，并按 §10.4 标注降级原因（`NoOdx`、`OdxMissingDefinition`、`NoFieldTable` 等） |
| 未知 SID/NRC | hex 回退，不抛异常 |
| 解析器明确标记为 CAN FD | 列入未支持输入及数量，不按 classic CAN 误解码 |
| 用户取消 | 返回 `IsPartial=true` 的当前文件部分报告 |
| 导出失败 | 在离线状态区显示失败原因，不静默吞掉 |

## 13. 报告导出

### 13.1 内容

Markdown 至少包含：

- 报告 ID、分析器版本、文件和地址配置、诊断定义来源与 `OdxLoaded` 标记。
- ODX 快照说明、时序来源和日志范围。
- 汇总计数（含 §7.4 闭合等式）、噪声汇总（非诊断帧总数与按 CAN ID 的 Top-N、未支持输入、无法成帧原因分布、`ResponseValidationFailed`、`DuplicateFinalResponse`）、逐事务结果、首次响应耗时和总耗时。
- 孤立响应、歧义响应、传输警告、不可知项和部分报告标识。
- 证据序号及允许导出的原始数据。

CSV 每行一个事务，保留报告 ID、证据首末序号和来源，不把多条响应挤成无法区分的文本；报告级计数以文件顶部 `# key=value` 汇总行输出（含闭合等式各项、`ResponseValidationFailed` 与 `DuplicateFinalResponse` 计数），再接事务表头，保证 CSV 单独拿去分析时口径仍闭合。

### 13.2 文件安全

沿用 NM 的成熟边界：

- 根据用户选择写 `.md` 或 `.csv`。
- 纠正扩展名后，如最终路径已存在，必须再次确认覆盖。
- 写文件失败在界面可见。
- 导出的是当前面板报告快照；新文件或新分析完成后，不得继续把旧快照冒充当前报告导出。

### 13.3 脱敏

每次导出都提供“脱敏 / 原样 / 取消”；关闭对话框等同取消。

脱敏报告：

- 保留时间、通道、CAN ID、SID、子功能、DID/例程 ID、NRC、长度和证据序号。
- 用占位标识替换完整本地路径和 ECU 身份。
- 不输出 SecurityAccess 种子和密钥。
- 不输出 DID 数据值及其解码物理值。
- 不输出下载、上传、刷写或其它敏感服务的业务载荷。
- 对敏感事务不输出可能经多帧拼接泄露内容的原始数据列，而不是只遮个别字节。

“原样导出”只影响本地文件，不改变 AI 的强制脱敏边界。

## 14. AI 对话 Handoff

按钮文案为“在 AI 中解读选中事务”。UDS 窗口不新增聊天界面、消息历史或提示词预览区，而是把当前脱敏问题交给项目已有 AI 对话。

### 14.1 调用链与窗口复用

```text
UdsLogAnalysisViewModel
  --> UdsOfflineAiPromptBuilder（当前报告快照 + 选中事务，强制脱敏）
  --> ITraceViewerChatHandoffService
  --> WindowHostService（打开或唤回 WindowKey.TraceViewer）
  --> TraceViewerViewModel.AcceptChatHandoff（新增）
  --> 现有 AI 对话页签、ChatInput、提示条与输入焦点
```

- Handoff 服务使用与 AppShell 相同的 `WindowHostService` 和 `TraceViewerViewModel` 工厂。
- AppShell 普通“打开追踪查看器”和 UDS Handoff 必须共用同一条开窗/激活路径，不复制窗口缓存逻辑。
- 窗口已打开时续用当前 ViewModel、聊天历史、Provider 设置和工具定义；窗口已关闭时按现有 transient 生命周期新建，不改变聊天持久化规则。
- 新增的 `AcceptChatHandoff` 复用 `PrefillChatInput`、`ChatPrefillHint`、`ChatPanelTabIndex` 和 `ChatInputFocusTicket` 的现有语义：选中 AI 页签、预填并聚焦，但不执行 `SendMessageCommand`。
- Handoff 不把 UDS 文件加载进 TraceViewer，不要求加载 DBC，也不改变当前曲线、锚点或监视列表。

### 14.2 防止串日志与串报告

Handoff 载荷至少包含：

- `ReportId`、UDS 文件来源标识和物理地址配置。
- 当前选中事务的服务、时间、NRC、耗时、证据序号、已知事实和不可知项。
- 报告级噪声口径：输入帧数、匹配诊断帧数、非诊断帧数与 Top-N CAN ID、噪声帧数、未支持输入数、`ResponseValidationFailed` 与 `DuplicateFinalResponse` 计数，以及是否存在 `UnknownService`。
- 诊断定义状态：`OdxLoaded`、定义来源，以及未加载 ODX 时 DID/例程按原始值显示的说明。
- 强制脱敏后的提示词。

`TraceViewerViewModel` 保存本次 Handoff 上下文。`BuildSystemMessage` 增加 UDS 离线分析规则：

- 当前问题来自指定 `ReportId` 的 UDS 离线报告。
- 追踪查看器中其它 trace、DBC、锚点和 NM 数据不是本次问题的证据，除非用户明确切换任务并提供新依据。
- 首版不新增 UDS AI 工具；模型只能使用 Handoff 中提供的事实，不得调用无关工具补造证据。
- 事务列表不等于总线上的全部流量；回答涉及“日志中没有/只有”这类断言时，必须先引用报告级噪声口径，不得把被过滤的非诊断帧当作不存在。
- 未加载 ODX 时不得把 DID/例程原始 hex 解释为异常或解析失败；需要解码能力时明确告知用户加载 ODX 并重新分析。
- 回答必须区分日志事实、假设和不可知，不把时间相关性写成确定因果。

### 14.3 草稿、发送与费用

- AI 输入框已有不同的未发送草稿时，先询问是否覆盖；取消则保留原草稿，不静默丢失。
- Handoff 本身不调用 `ILlmProvider`、不访问网络、不产生模型费用。
- 只有用户在现有 AI 面板手动发送后，才沿用当前 Provider 的网络、计费、错误处理和聊天历史。
- AI 输入始终脱敏，不提供“向 AI 发送原始种子/密钥/DID 值”的选项。

## 15. 测试设计

### 15.1 Core 单元测试

建议位于 `tests/PeakCan.Host.Core.Tests/Analysis/Uds/`。

**ISO-TP：**

- 单帧请求和响应。
- 请求方向多帧、响应方向多帧及双向交错。
- 连续帧序号回绕、错误序号、非法 PCI、DLC 不足和无在途 PDU 的连续帧。
- 不同通道、不同 ID、同数值标准/扩展 ID 的交错隔离。
- 方向 `Unknown` 的帧仍参与正确地址的数据流。
- 新 First Frame 覆盖和日志结束时的不完整 PDU。
- 分析器没有发送接口；App 层集成测试在硬件边界用发送 spy 断言零发送。

**事务配对：**

- 直接正响应、最终 NRC、一次及多次 `0x78` 后成功。
- 日志结束仍 pending。
- 超过 P2 后迟到响应仍完成原事务。
- 无匹配请求的孤立响应。
- 不同 SID 重叠分别闭合。
- 相同 SID 重叠后的响应不得计为确定成功。

**噪声分类与计数：**

- 混合日志（本地址诊断帧 + 其他 ID 周期帧 + 非法 PCI 帧 + CAN FD 帧）满足 §7.4 闭合等式。
- 地址匹配但 PCI 非法的帧进入噪声桶，带原因与证据序号，不创建事务。
- 未知 SID 但成帧合法 → 建事务并标 `UnknownService`，不丢弃。
- 以 `0x76` 开头但长度或回显不符的周期帧不闭合 TransferData 事务，请求保持未闭合。
- 校验失败后收到合法响应，原事务仍能正常闭合，且校验失败帧不计入首次响应耗时、不进孤立集合。
- 同一请求收到两个最终响应 → 第二个不静默变孤立，事务标 `DuplicateFinalResponse`，不计确定成功。
- 无在途 PDU 的连续帧（日志从传输中段开始）进噪声桶；序号错误只把出错帧计入噪声，已收 FF/CF 保留匹配分类。
- 流控帧计入匹配诊断帧数但不形成 PDU；畸形 FC 进噪声桶。
- 地址不匹配的 CAN FD 帧进未支持输入桶，而非诊断帧桶。
- 两字节 `50 02` 不闭合 `0x10` 事务（长度 < 6）。
- 非诊断帧按 CAN ID 聚合的 Top-N 与计数稳定，不随日志帧顺序变化。

**时序：**

- `P2=0x0032` 得到 50 ms。
- `P2*=0x01F4` 得到 5000 ms，而非 500 ms。
- 未取得 `0x10` 正响应前时序来源为未知。
- 新时序不影响更早事务，也不修改在线 `UdsTimer`。
- 首次响应耗时与事务总耗时在多帧场景下分别可手算复现。

**解释与报告：**

- DID ODX 解码、未知 DID、缺失字段和短 payload 回退。
- 分析期间替换共享 DID 数据库不改变已生成报告。
- 未加载 ODX 时 5 个内置 DID 仍显示名称与期望长度，字段级解码按 `NoFieldTable` 回退原始 hex；无任何来源定义的 DID/例程原因为 `NoOdx`。
- 已加载 ODX 但缺少某 DID → 原因为 `OdxMissingDefinition`，与 `NoOdx` 可区分。
- 分析后再加载 ODX 不改变当前报告；重新分析才采用新定义。
- 报告、导出与 AI 载荷携带 `OdxLoaded`、定义来源和 `EngineVersion`；`OdxLoaded` 与用户 JSON 加载状态取自各自权威来源，不从 `All` 反推。
- 用户 JSON 的未配置 / 文件缺失 / 加载成功 / 解析失败四种状态能正确传递到报告。
- 未知 SID/NRC 使用 hex。
- 取消后的报告只包含已完成阶段，且标记部分结果。

### 15.2 App 与 XAML 测试

建议位于现有 App 测试项目的 UDS ViewModel/Views/Services 区域：

- 默认离线页签隐藏在线控制、通信参数和在线输出日志。
- 切回在线页签恢复原布局，在线行为不被离线任务改变。

- 报告摘要显示“未加载 ODX”状态；AI 提示词包含 `OdxLoaded=false`，不把原始值写成异常。
- 刷写中警告在离线页签仍可见。
- 未连接硬件、未加载 DBC 时能够完成分析，硬件发送 spy 计数为零。

- 报告摘要显示输入帧数、匹配诊断帧数、非诊断帧数、噪声帧数、未支持输入数和 Top-N CAN ID；截断时显示“聚合已截断”。

- AI 提示词不含种子、密钥、DID 值；Handoff 不执行发送命令且 Provider spy 调用为零。手动发送仍走现有 Provider 路径。

### 15.3 ASC/BLF golden 端到端

为同一组诊断场景准备等价的小型 ASC 与 BLF 日志，覆盖：

- 多帧 DID 成功。
- 连续 `0x78` 后成功。
- 最终 NRC。
- 未闭合请求。
- 同一时刻混入其他 CAN ID 的周期应用报文（噪声）。
- 无 DBC、无硬件连接。

两种格式解析后的规范化报告应得到相同事务、NRC、pending 次数、耗时、证据顺序和噪声分类计数；文件格式元数据不参与等价比较。

### 15.4 变异验证

至少执行以下变异，证明测试探针会响：

| 变异 | 必须变红的测试 |
|---|---|
| 删除 P2* 的 ×10 换算 | P2* 单位判别测试 |
| 把每个 `0x78` 创建成独立事务 | pending 聚合测试 |
| 丢弃方向未知的帧 | 方向未知配对测试 |
| P2 超阈值时提前删除在途请求 | 迟到响应测试 |
| 删除噪声桶或漏算一类帧 | 计数闭合测试 |
| 去掉响应最小长度/回显校验 | 伪 `0x76` 响应测试 |
| 把第二个最终响应静默归入孤立响应 | 重复最终响应测试 |
| 脱敏仅遮 SecurityAccess 首字节而保留剩余密钥 | 多帧/完整敏感载荷泄漏测试 |

变异还原后清理构建缓存，再取干净树读数。

## 16. 验收标准

1. 在硬件断开且未加载 DBC 的条件下打开 ASC 和 BLF，均能得到请求—响应事务。
2. 多帧 DID 能正确重组，并按分析开始时的诊断定义快照解码；无 ODX 时保留完整原始值。
3. 连续 `0x78` 只形成一个事务，首次响应耗时与总耗时分别可见。
4. NRC、孤立响应、归属歧义、重复最终响应、响应校验失败噪声和未闭合有不同且可验证的界面状态。
5. “未看到响应”的文案不被写成“ECU 未发送”。
6. P2/P2* 有明确来源，P2* 单位判别测试通过。
7. 离线分析和 AI Handoff 本身没有硬件连接、CAN 发送、自动流控或 LLM 网络调用；只有用户手动发送才进入现有 Provider。
8. 取消产生可辨识的部分报告；换文件不会残留旧报告。
9. 导出和 AI 使用同一报告快照；Handoff 复用现有 AI 对话且防止串日志，脱敏规则由泄漏测试证明。
10. 现有在线 UDS 测试和全量回归保持通过；本需求不改变在线 P2* 或其它在线缺陷的现状。
11. 报告满足 §7.4 计数闭合等式；非诊断帧可按 CAN ID 聚合查看，导出与 AI 提示词使用同一噪声口径。
12. 响应 ID 上的非诊断帧不会被静默判为最终响应；校验不通过不会闭合事务，日志结束时仍未收到通过校验的响应则保持未闭合并给出原因。
13. 未加载 ODX 时仍生成完整报告：内置 DID 仍能标识名称与期望长度，字段级解码按原因回退原始值；界面、导出和 AI 提示词明确标注未加载 ODX。
14. 离线页保留共享“加载 ODX…”入口；加载只影响下一次分析，不热更新当前报告。
15. 报告、导出与 AI 载荷携带 `EngineVersion` 及 §7.4 闭合等式的各项计数。

## 17. 风险与后续扩展

- **全量解析内存**：首版以 200 MB 为明确边界；超限时如实拒绝，不通过静默截断制造“完整报告”。未来若现场日志证明该上限不足，再单独立项统一流式时间基准和重组状态。
- **重叠同 SID**：首版保守标记歧义，宁可少报确定成功，也不伪造归属。
- **同 ID 噪声**：日志方向标记不可信（D6），在线刷写块序号缺陷也不在本需求范围；首版用离线长度/回显校验降低误判，校验失败帧进噪声桶，重复最终响应显式标记 `DuplicateFinalResponse`。并行诊断源与本人重试无法从日志裁决，报告必须保留这一不可知项。
- **共享 ODX**：当前报告不随共享数据库热更新；用户通过重新分析显式采用新定义。
- **敏感日志**：SecurityAccess、DID 和刷写数据可能经多帧重组泄露，脱敏必须覆盖完整事务和原始帧输出，而非只替换界面摘要。
- **AI 上下文串联**：复用现有对话并不等于可以复用其它日志证据；Handoff 必须携带报告身份，系统提示必须隔离无关 trace/DBC/NM 上下文。
- **协议扩展**：多 ECU、CAN FD 和 DoIP 都需要各自独立的配对/重组规则与验收夹具，不在首版通过条件分支假装支持。
  <br/>**2026-11-27 更新**：功能寻址已单独落地（`UdsOfflineAddress.FunctionalId` + 分类器 `IsFunctional` 判定），
  不再属于「假装支持」——它有独立契约和验收测试。多 ECU 仍不做。
