# J1939TP 多帧传输与 GBT27930 支持 — 设计文档

- 日期：2026-08-29
- 状态：Draft（待用户 review）
- 分支：`feat/j1939tp-gbt27930`
- 相关先例：`Uds/IsoTp/IsoTpLayer`（协议层模板）、`IsoTpSinkAdapter`（路由器接线）、`SequenceLibrary`（JSON 持久化）、`TraceViewerViewModel`（回放分析）

---

## 1. 背景与目标

peakcan-host 需要支持 SAE J1939-21 传输协议（TP），首要目标场景是 **GB/T 27930-2015**（电动汽车传导充电 BMS ↔ 充电机通信）：

- 250 kbps 经典 CAN、29 位扩展帧
- 固定地址：充电机 `0x56`、BMS `0xF4`
- 所有多帧报文走 **BAM** 广播（GBT27930 不用 RTS/CTS）
- 多帧报文典型数十字节级（如 BRM 车辆辨识报文，6 个 TP.DT 包）

功能目标三项：

1. **收发**：J1939TP 多帧发送（BAM + RTS/CTS）与接收重组；
2. **分析**：Trace Viewer 对 ASC/BLF 回放做 TP 重组 + DBC 信号级解码；
3. **仿真**：轻量节点抽象（`SimulatedNode`），支持扮演充电机或 BMS。

非目标（明确排除，YAGNI）：

- GBT27930 应用层状态机（CHM→CRM→BCP→充电→结束 的自动协商流程）——后续独立 feature；
- J1939 地址声明（Address Claim, PGN 60928）的完整管理——仅留节点级可选开关，默认关闭；
- CAN FD 上的 J1939（J1939-17/-22）；
- ISO-TP 与 J1939TP 的统一抽象（两者差异大，强行抽象只会增加耦合；各自独立实现，共享的只是工程模式）。

## 2. 范围

| 项 | 范围 |
|---|---|
| TP 模式 | **BAM + RTS/CTS 完整实现**（用户决策：面向通用 J1939 场景，不只 GBT27930） |
| Trace Viewer 解析 | **L2 重组消息视图 + L3 虚拟帧注入 DBC 解码**（L1 行内注解顺带做） |
| 节点仿真 | **SimulatedNode B1（周期消息表）+ B2（响应规则表）**；B3 复杂时序状态机不做 |
| CTS 流控策略 | 可配置，默认放行全部剩余包（J1939-21 接收方常规行为） |

## 3. 现状资产盘点

实现完全建立在现有模式上，不引入新分层概念：

| 现有资产 | 位置 | 复用方式 |
|---|---|---|
| `IsoTpLayer`（partial class 分 ReceiveFlow/SendFlow/WatchdogFlow/LoggingFlow） | `src/PeakCan.Host.Core/Uds/IsoTp/` | `J1939TpLayer` 的目录结构与工程模式模板（watchdog、防御性长度校验、锁保护重组、source-gen 日志） |
| `IsoTpFrame` 纯编解码 record struct | 同上 | `TpCm`/`TpDt` 编解码照此 |
| `IsoTpSinkAdapter : IFrameSink` | `src/PeakCan.Host.App/Composition/` | `J1939TpSinkAdapter` 照抄其窄捕获 `ArgumentException` 策略 |
| `ChannelRouter` fan-out（per-sink 异常隔离） | `src/PeakCan.Host.Infrastructure/Channel/` | 协议层作为旁路 sink 挂接，不动 Trace/Record/Stats 帧流 |
| `ICanChannel.WriteAsync` + `SendService` / `ICyclicSendService` | Infra/App | 发送底座，无需新增硬件代码 |
| `ITraceViewerService.LoadedFrames` → `ReplayFrame` | Core/App | 离线重组输入；L3 虚拟帧沿用同一类型 |
| `SignalDecoder.Decode(data, sig)` + DBC `MessagesById` | Core | L3 信号解码零改动复用 |
| `SequenceLibrary`（JSON、atomic write、`%APPDATA%`） | App | `NodeConfigLibrary` 持久化模板 |
| `FrameFormat.Extended` / `ReplayFrame.IsExtended` 全链路 | 各处 | 29 位 ID 无障碍 |

**为何不复用 `IsoTpLayer` 本体**：ISO-TP 是单会话、PCI 内嵌、12 位长度、点对点；J1939TP 是多会话并发（按 (SA, DA) 键）、TP.CM/TP.DT 独立 PGN、16 位包数、含广播模式。协议机制差异过大，但工程模式（文件切分、watchdog、防御、日志）100% 照搬。

## 5. Core 层设计

### 5.1 J1939Id（纯函数值类型）

```csharp
// src/PeakCan.Host.Core/J1939/J1939Id.cs — namespace PeakCan.HIL.Core.J1939
public readonly record struct J1939Id(uint Raw)
{
    public byte Priority { get; }        // bits 26-28 (3 bits)
    public byte ReservedEdp { get; }     // bit 25（GBT27930 恒 0；计入 PGN bit 17）
    public byte DataPage { get; }        // bit 24
    public byte PduFormat { get; }       // bits 16-23 (PF)
    public byte PduSpecific { get; }     // bits 8-15  (PS)
    public byte SourceAddress { get; }   // bits 0-7   (SA)
    public bool IsPdu1 => PduFormat < 240;

    // PGN 按 18 位计算：bit17=ReservedEdp, bit16=DP, bits15-8=PF, bits7-0=PDU2?PS:0。
    // GBT27930 帧 R/EDP=0，与忽略该位的算法结果一致；通用 J1939 不丢信息。
    public uint Pgn { get; }

    public byte? DestinationAddress => IsPdu1 ? PduSpecific : null;

    // 唯一合法的 ID 组合入口——所有调用方（含 §9.3 虚拟帧）禁止手写位运算。
    public static uint Compose(byte priority, uint pgn, byte sa);
}
```

### 5.2 TP.CM / TP.DT 字节布局（0-indexed）

TP.CM：PGN 60416 (`0x00EC00`)，PDU1，CAN ID 中 PS = 目标地址（BAM 时 `0xFF`）。
TP.DT：PGN 60160 (`0x00EB00`)，PDU1，同上。

| 消息 | [0] | [1] | [2] | [3] | [4] | [5..7] |
|---|---|---|---|---|---|---|
| RTS | `0x10` | total size LE | | total packets | `0xFF` | PGN LE 3B |
| CTS | `0x11` | max packets/CTS | next packet # | `0xFF` | `0xFF` | PGN LE 3B |
| EOM_ACK | `0x13` | total size LE | | total packets | `0xFF` | PGN LE 3B |
| BAM | `0x20` | total size LE | | total packets | `0xFF` | PGN LE 3B |
| ConnAbort | `0xFF` | reason | `0xFF` | `0xFF` | `0xFF` | PGN LE 3B |
| TP.DT | seq #(1-based) | data[0..6]（末帧不足填 `0xFF`） | | | | |

PGN 3 字节小端：`[5]` = PGN bits 0-7（PDU2 的 PS；PDU1 为 0），`[6]` = PF，`[7]` = DP。

编解码类型镜像 `IsoTpFrame` 的**单 record + enum + 按类型解释字段**形态（不用判别联合——与既有代码保持一致，测试矩阵可对照）：

```csharp
// src/PeakCan.Host.Core/J1939/Tp/TpCmMessage.cs
public enum TpCmControl : byte { Rts = 0x10, Cts = 0x11, EomAck = 0x13, Bam = 0x20, ConnAbort = 0xFF }

public readonly record struct TpCmMessage(
    TpCmControl Control,
    ushort TotalSize,        // RTS/EomAck/Bam 有效；Cts/ConnAbort 无意义置 0
    byte TotalPackets,       // RTS/EomAck/Bam 有效
    byte MaxPacketsPerCts,   // 仅 Cts 有效；0 = hold / 接收方策略放行全部（语义依上下文，见 §6.2）
    byte NextPacketNumber,   // 仅 Cts 有效（1-based）
    byte AbortReason,        // 仅 ConnAbort 有效
    uint Pgn)                // 恒有效（18 位 PGN，语义同 J1939Id.Pgn）
{
    public byte[] Encode();                       // 恒返回 8 字节
    public static TpCmMessage Decode(ReadOnlySpan<byte> data);  // 畸形 → ArgumentException
}

// src/PeakCan.Host.Core/J1939/Tp/TpDtMessage.cs
public readonly record struct TpDtMessage(byte SequenceNumber, ReadOnlyMemory<byte> Data)
{
    // Encode：Data 不足 7 字节自动 0xFF 填充（调用方不传填充字节）；
    // SequenceNumber 范围 1..255，越界 → ArgumentException。
    public byte[] Encode();                       // 恒返回 8 字节
    // Decode：Data 恒为 7 字节（不去尾 0xFF——是否截尾由重组层按 TotalSize 决定）。
    public static TpDtMessage Decode(ReadOnlySpan<byte> data);  // 长度<8 → ArgumentException
}
```

Decode 对畸形输入抛 `ArgumentException`，由 sink adapter 窄捕获——与 ISO-TP 路径同一契约。

### 5.3 J1939TpLayer（partial class，镜像 IsoTpLayer 目录）

**构造与公开 API**（签名定死，委托签名与 `IsoTpLayer` 同形——实现时对照 `IsoTpLayer.cs` 实际签名取齐）：

```csharp
// src/PeakCan.Host.Core/J1939/Tp/J1939TpLayer/J1939TpLayer.cs
public sealed partial class J1939TpLayer
{
    // sendAsync：帧写出委托。生产环境由 App 层用现有 SendService 适配注入；
    // Core 不依赖 ICanChannel / ISendService（分层约束同 IsoTpLayer）。
    public J1939TpLayer(
        Func<CanFrame, CancellationToken, ValueTask<Result<Unit>>> sendAsync,
        J1939TpOptions options,
        ILogger<J1939TpLayer>? logger = null);

    public void ProcessFrame(CanFrame frame);      // 同步、非阻塞；畸形帧抛 ArgumentException
    public Task<Result<Unit>> SendBamAsync(uint pgn, byte priority, byte sa,
        ReadOnlyMemory<byte> payload, CancellationToken ct = default);
    public Task<Result<Unit>> SendRtsCtsAsync(uint pgn, byte priority, byte sa, byte da,
        ReadOnlyMemory<byte> payload, CancellationToken ct = default);

    // 本机身份注册（NodeHostService 在节点 Start/Stop 时调用；线程安全）。
    public void RegisterLocalAddress(byte sa);
    public void UnregisterLocalAddress(byte sa);

    public event Action<J1939Message>? MessageReceived;
    public event Action<J1939SessionEvent>? SessionEvent;
}
```

**线程模型（契约，写进 xmldoc）**：

- `ProcessFrame` 在生产环境运行于 SDK 读线程（经 ChannelRouter 分发）。两个事件都在**调用 ProcessFrame 的线程**上同步触发——订阅方必须非阻塞，需要 UI 更新的自行 marshal（与 `ITraceViewerService.FrameEmitted` 的既有注释风格一致）；
- 接收方自动回 CTS/EOM_ACK 的发送在 `ProcessFrame` 内 **fire-and-forget**（不 await；发送异常内部捕获 + LogError，绝不抛回读线程）；
- 事件 handler 调用在锁外 + try/catch 隔离（同 `IsoTpLayer` v1.2.12 Item 3 模式）。

**OfflineMode 语义**（`J1939TpOptions.OfflineMode`，回放分析专用）：`true` 时 ① 不启实时 watchdog；② 禁止一切主动发送（CTS/EOM_ACK/ConnAbort 一律不发，即使 RTS 命中 `_localAddresses`）；③ 完整性判定移交调用方（§9.2）。

**会话表**——与 ISO-TP 单会话最大的结构差异：

```csharp
// DT 帧不含 PGN，会话归属按 (SA, DA) 匹配；PGN 存于会话内。
// BAM: Da = 0xFF；RTS/CTS: Da = 对端地址。
readonly record struct SessionKey(byte Sa, byte Da);

internal sealed class TpSession
{
    uint Pgn; byte Priority; TpMode Mode;        // BAM | RtsCts
    int TotalBytes; int TotalPackets;
    int NextExpectedSeq;                          // 1-based
    byte[] Buffer; int Received;
    long LastFrameTicks;                          // watchdog 基准（Stopwatch）
    // RTS/CTS 发送方附加状态：等待 CTS / 段内剩余可发数 / 等待 EOM_ACK
}

Dictionary<SessionKey, TpSession> _sessions;      // 多会话并发

// 本机身份：NodeHostService 启动/停止节点时注册/注销对应 SA。
// 仅当 RTS 的 DA ∈ LocalAddresses 时才回 CTS —— 纯监听场景该集合为空，
// 协议层只被动重组，绝不向真实总线注入 TP.CM，避免干扰真实桩/车通信。
HashSet<byte> _localAddresses;
```

约束与防御（镜像 `MaxMessageLength` 思路）：

- `J1939TpOptions.MaxPayloadBytes`（默认 1785 = 255×7）——RTS/BAM 宣告长度超限直接丢弃；
- `J1939TpOptions.MaxConcurrentSessions`（默认 32）+ LRU 驱逐——防 fuzz 打爆内存；
- 同一 (SA, DA) 收到新 RTS/BAM → 旧会话被取代（J1939 允许 restart），作废事件上报。

**事件输出**（`src/PeakCan.Host.Core/J1939/J1939Message.cs`）：

```csharp
public enum TpMode : byte { Bam = 0, RtsCts = 1 }

public sealed record J1939Message(
    uint Pgn, byte Sa, byte Da, byte Priority,
    TpMode Mode,
    byte[] Payload,
    // 时间戳恒为 double 秒。实时路径由 CanFrame.Timestamp(us) 除以 1e6 换算；
    // 协议层只做单位换算，不归一化基准（实时=源通道基准，回放=录制起点）——
    // 基准对齐是消费方（Trace Viewer）的职责。
    double FirstFrameTimestampSec,     // TP.CM 帧时间（Seek 跳转用）
    double CompletedTimestampSec);     // 末帧时间（消息完成时刻，显示/解码用）

public enum SessionEventKind : byte { Superseded, PacketLoss, Timeout, Evicted }

public sealed record J1939SessionEvent(
    SessionEventKind Kind, byte Sa, byte Da, uint Pgn, TpMode Mode, string Detail);
```

### 5.4 超时参数（`J1939TpOptions`，默认值实现时以 J1939-21 §5.10 核对）

| 参数 | 默认 | 含义 |
|---|---|---|
| `T1Ms` | 750 | 接收方等下一 TP.DT |
| `T3Ms` | 1250 | 发送方等 CTS / EOM_ACK 上限 |
| `T4Ms` | 1050 | CTS hold（max packets=0）后等待上限 |
| `BamIntervalMs` | 50 | BAM 的 TP.DT 帧间隔（J1939-21 允许 50–200；GBT27930 实测设备常用 10–50，可下调） |
| `CtsMaxPackets` | 0 | 接收方每 CTS 放行包数；0 = 放行全部剩余（默认） |
| `MaxPayloadBytes` | 1785 | 长度防御 |
| `MaxConcurrentSessions` | 32 | 会话表防御 |

watchdog 用 `Stopwatch` 打点 + 单一定时器扫描会话表（不为每会话建 timer——会话数可达 32）。**扫描周期固定 100ms**（最小超时 T1=750ms 的 1/7，判定精度足够；离线模式不启动）。时钟抽象用 `TimeProvider`（.NET 8+），生产注入 `TimeProvider.System`，测试注入 `FakeTimeProvider`（`Microsoft.Extensions.TimeProvider.Testing` 包）——与发送间隔、超时的单测确定性要求一致。

## 6. 发送设计

### 6.1 BAM（`SendFlow.cs`）

```csharp
Task<Result<Unit>> SendBamAsync(
    uint pgn, byte priority, byte sa,
    ReadOnlyMemory<byte> payload, CancellationToken ct);
```

流程：校验长度 → 构造 TP.CM(BAM)（`J1939Id.Compose(priority, TpCmPgn, sa)`，PS=`0xFF`）→ `sendAsync` 写出 → 按 `BamIntervalMs` 间隔发 TP.DT #1..#N（PF=`0xEB`）→ 完成。

**契约（写进 xmldoc）**：

- 长度校验矩阵：`payload.Length == 0` → `Result.Error`；`1..8` → `Result.Error("≤8 字节应直接发单帧，不走 TP")`；`9..1785` → 正常 BAM；`> 1785` → `Result.Error`；
- 返回的 `Task` 在**最后一帧 TP.DT 写出后**完成（调用方可 await 完整发送周期）；
- `ct` 取消即中止（已发出的帧不回收；GBT27930 充电流程随时中断，取消是一等公民）；
- 发送失败（`sendAsync` 返回 Error）→ 中止并上报，不重试（重试策略归上层）；
- 并发：多个 `SendBamAsync` 并发合法（帧交错发出）；**同 (PGN, SA) 的并发发送由调用方避免**，协议层不检测。

### 6.2 RTS/CTS（`RtsCtsFlow.cs`）

发起方状态机：

```
SendRtsCtsAsync(pgn, prio, sa, da, payload, ct)
  → 发 RTS → [waitCTS: T3]
  → 收 CTS(maxPackets, nextPacket)
      · maxPackets=0 → hold，[waitNextCTS: T4]
      · 否则发 DT 段（nextPacket 起 maxPackets 个）
  → 段发完 → 全部发完? [waitEOM_ACK: T3] : [waitCTS: T3]
  → 收 EOM_ACK（校验 size/packets 一致）→ Ok
  → 任意时刻：收 ConnAbort / 超时 → Error(reason)
```

接收方角色（被对端 RTS 呼叫且 DA 属于本机身份集合 `_localAddresses` 时，协议层自动响应；总开关 `AutoRespondToRts` 默认开，但 `_localAddresses` 为空时效果等同关闭——纯监听安全）：

```
收 RTS → 建会话 → 回 CTS(maxPackets=CtsMaxPackets, nextPacket=1)
收 DT  → 序号校验 → 收满 CTS 声明数
      → 未完: 回下一个 CTS(nextPacket = 已收包数+1)；完成: 回 EOM_ACK + MessageReceived
T1 超时 → 会话作废（可选发 ConnAbort，开关默认关）
```

CTS 帧识别：按 (SA, DA) 匹配——注意方向反转（我们发 RTS 后，对端 CTS 的 SA=对端、DA=我们）。

`SendRtsCtsAsync` 契约：长度校验矩阵、Task 完成时机（收 EOM_ACK 后完成）、取消/失败语义与 `SendBamAsync` 相同（§6.1）；同一 (SA, DA) 同时只允许一个 RTS/CTS 发送状态机（J1939 限制），重入调用立即 `Result.Error`。接收方会话键为 (SA=对端, DA=本机)——与发送方会话不同键，互不干扰。

## 7. 接收重组（`ReceiveFlow.cs`）

```
ProcessFrame(CanFrame f)
  → J1939Id 解析；非扩展帧/PF 非 0xEB/0xEC → return
  → PF=0xEC (TP.CM):
      · BAM   → 建/取代会话（Da=0xFF）
      · RTS   → AutoRespondToRts 开 且 Da ∈ _localAddresses → 建会话 + 回 CTS（§6.2 接收方）
      · CTS/EOM_ACK/Abort → 路由到 RtsCtsFlow 的发送方状态机
  → PF=0xEB (TP.DT):
      → 按 (SA, DA) 找会话；无会话 → 丢弃（不计错误，总线上常见半截流量）
      → 序号 != NextExpectedSeq → 会话作废 + SessionEvent(PacketLoss)
      → 追加数据；收满 → MessageReceived + 会话移除
```

## 8. App 层接线

### 8.1 J1939TpSinkAdapter（Composition/）

照抄 `IsoTpSinkAdapter`：`IFrameSink.OnFrame` 窄捕获 `ArgumentException`（防畸形帧导致路由器自动 detach）、`OnError` 只记录不动作、满足 sink 不抛异常契约。由 `SinkWiringService` 统一挂接（与现有 sink 同一入口）。

**DI 生命周期**：`J1939TpLayer` **每通道一个 DI singleton**，在 `AppHostBuilder`/`CoreInfrastructureFlow` 参照 UDS stack（`SecondaryFlashStack`）的既有注册点创建；`sendAsync` 委托由该通道的 `SendService` 适配生成。`J1939TpSinkAdapter` 与 layer 同生命周期。

### 8.2 J1939SendViewModel

发送面板定死为 **Send 窗口内新增 J1939 子面板**（与现有 MultiFrame 子面板并列的 section，不开新 tab、不开新窗口；XAML 线框在 plan 阶段按现有 `SendView` 布局出图）：PGN(hex) / 优先级 / SA / DA(RTS-CTS 时) / TP 模式(BAM | RTS-CTS) / payload hex / 周期 ms（0=单次）/ BAM 间隔高级项。周期调度**复用外层周期服务模式**（镜像 `CyclicDbcSendService` 对 `ICyclicSendService` 的用法），定时器不进 Core 层。

## 9. Trace Viewer：L1 / L2 / L3

### 9.1 L1 行内注解（低成本顺带做）

帧列表对 PF=0xEB/0xEC 帧增加解码列：`TP.CM BAM PGN=0x000204 len=41 pkts=6`、`TP.DT #3/6`、`TP.CM RTS …`。纯显示层，不重组。

### 9.2 L2 重组消息视图

`J1939ReassemblyService`（`src/PeakCan.Host.App/Services/J1939/`，无 UI 依赖，可单测）：

```csharp
public sealed class J1939ReassemblyService
{
    // 输入为单个 trace 源的帧列表；多源会话由调用方（VM）逐源调用，本服务不做源合并。
    // 返回列表按 CompletedTimestampSec 升序。
    public IReadOnlyList<ReassembledJ1939Message> Reassemble(IReadOnlyList<ReplayFrame> frames);
}

public enum ReassemblyStatus : byte { Complete, Truncated, PacketLoss }

public sealed record ReassembledJ1939Message(J1939Message Message, ReassemblyStatus Status);
```

**帧适配（契约）**：`ProcessFrame` 只吃 `CanFrame`，回放输入是 `ReplayFrame`——服务内部逐帧适配（`ReplayFrame.Timestamp` 秒 → `Timestamp(us×1e6)`、`IsExtended` → `FrameFormat`、mask IDE bit，转换位逻辑与 `TraceDrivenChannel.ToCanFrame` 相同；该方法现为 private，plan 阶段决定提取共享 helper 还是复写，二选一在 plan 里定死）。适配后喂给**同一个** `J1939TpLayer` 类型的新实例，构造为**离线模式**（`J1939TpOptions.OfflineMode = true`，`sendAsync` 注入恒失败的桩——离线禁止发送的兜底）：

- 不启动实时 watchdog（ASC 帧间隔是录制值，不代表健康度）；
- 完整性判定改为：序号连续 + 文件结束时 `NextExpectedSeq > TotalPackets` 视为 Complete，否则 Truncated；序号跳变 → PacketLoss。

完整性判定（离线模式契约）：序号连续 + 输入结束时 `NextExpectedSeq > TotalPackets` → Complete，否则 Truncated；序号跳变 → 该会话产出 PacketLoss 行（保留已收部分字节）后继续处理后续帧。判定在 `Reassemble` 返回前统一结算（遍历完输入后，对所有未闭合会话做一次终态评估）。

UI：重组视图面板（DataGrid）：完成时间、SA、PGN(hex+DBC 名)、模式、长度、状态、payload hex。双击行 → 跳转 TP.CM 帧（复用 `TraceViewerViewModel` 现有 Seek 命令管线，与 AI Chat 工具的 Seek 同路径）。

### 9.3 L3 虚拟帧注入 DBC 解码

重组完成的消息包装为虚拟 `ReplayFrame`（ID 组合一律走 `J1939Id.Compose`，禁止手写位运算）：

```csharp
new ReplayFrame(
    Timestamp: msg.CompletedTimestampSec,
    Id: J1939Id.Compose(msg.Priority, msg.Pgn, msg.Sa),  // 29 位 J1939 全 ID
    Dlc: (byte)Math.Min(msg.Payload.Length, 0xFF),       // GBT27930 均 <256B；>255 时以 Data.Length 为准
    Data: msg.Payload,
    Flags: FrameFlags.None,
    IsExtended: true);
```

**注入点（决策定死）**：`ITraceViewerService.LoadedFrames` 是只读视图，**不改 Core 接口**。在 App 层（`TraceViewerViewModel` 的信号解码路径）构造**增强帧序列**：原始帧 ∪ 虚拟帧按 `Timestamp` 归并排序（稳定排序，同刻原始帧在前），作为 `SignalDecoder`、watch 表、图表、AI Chat 工具的解码输入——全部零改动生效。归并逻辑抽为 `J1939VirtualFrameMerger` 静态类（`Services/J1939/`，纯函数可单测）。

**DBC ID 匹配回退**（`J1939VirtualFrameMerger` 内实现）：J1939 DBC 的 message ID 惯例不一（有的含 priority 位，有的仅 `PGN<<8|SA`）。查询顺序：① 精确 29 位 ID → ② mask priority（`id & 0x03FFFFFF`）→ ③ PGN 段匹配（`id & 0x03FFFF00`）。首个命中级别即停；命中级别写入 Debug 日志（不弹 UI），同一 DBC 文档的级别判定结果缓存。

## 10. SimulatedNode 轻量节点（方案 B：B1+B2）

**定位**：可保存、可一键启停的"虚拟 ECU 角色"（剩余总线仿真的最小实现）。被测件（真实充电桩/BMS）需要通信对端才进入充电流程；SimulatedNode 把"周期发哪些报文 + 收到什么回什么"组织为一个整体配置单元，JSON 即角色档案。

**边界（正交性）**：SimulatedNode 是协议层的**第三种消费方式**，与现有功能互不依赖：

| 功能 | 与 SimulatedNode 的关系 |
|---|---|
| Send 面板（§8.2 手动/周期 BAM、RTS-CTS） | 直连 `J1939TpLayer`，**不经过**节点；发一条测一测无需建节点 |
| Trace Viewer（§9 L1/L2/L3） | 只消费帧流与 `MessageReceived` 事件，**不经过**节点；无节点时重组分析照常 |
| DBC | **全局一份**（现有 `DbcService` singleton），节点不持有 DBC 副本；`DbcSignals` payload 来源只存对全局 DBC 的消息名/信号名引用（同 CANoe：DBC 全局加载，节点引用消息定义） |

**通用性**：核心抽象**不为 J1939 专用**——身份 + 周期消息表 + 响应规则表对经典 CAN 同样成立（模拟 ECU 周期发帧、响应诊断请求）。设计为通用核心 + 消息引用分层，J1939 是首个后端：

```csharp
// App 层 Services/Nodes/ —— 通用核心
sealed class SimulatedNode : IDisposable
{
    string Name;
    NodeIdentity Identity;           // { string? Channel } + 后端身份（J1939: SA）
    INodeBehavior Behavior;          // 行为模型（扩展锚点 1）
    NodeRuntimeState Runtime;        // 运行时信号值表（扩展锚点 3）
    void Start(); void Stop();       // 节点级启停
}

// ── 扩展锚点 1：行为模型抽象。节点不直接持有消息表/规则表，
//    B3 状态机、脚本行为以并列实现加入，不改节点类。
interface INodeBehavior
{
    void Attach(INodeContext ctx);   // ctx 注入：发送能力 + 消息到达事件 + 时钟
    void Detach();
}
sealed class RuleBasedBehavior : INodeBehavior   // 本期：B1 周期表 + B2 ECA 规则表
{
    IReadOnlyList<NodeMessage> Messages;
    IReadOnlyList<ResponseRule> Rules;
}
// 后续：StateMachineBehavior（B3 多步协商/重试）、ScriptBehavior

// ── 消息引用判别联合（System.Text.Json 多态，"kind" discriminator）
abstract record MessageRef;
sealed record J1939MessageRef(uint Pgn, byte Priority, TpMode Mode, byte? Sa) : MessageRef;  // 本期实现
sealed record CanMessageRef(uint Id, bool IsExtended) : MessageRef;   // 经典 CAN，后续按需（本期不做）
// 扩展锚点 2：触发 SA 归位 J1939MessageRef.Sa，通用层不见 J1939 概念；
// 规则匹配由各后端解释自己的 MessageRef 子类。

// ── 扩展锚点 3：payload 来源判别联合 + 每周期 live 求值。
//    DbcSignals 引用全局 DbcService 的消息/信号名，值存节点 Runtime 表；
//    SetSignalValue(msg, signal, value) 运行时改、下一周期生效。
abstract record NodePayloadSource;   // 本期：FixedHex | DbcSignals | ScriptCallback
// 将来加子类即可：CounterCrcSource（rolling counter + E2E CRC）、SignalGeneratorSource（斜坡/正弦）

sealed record NodeMessage(
    MessageRef Ref,
    int IntervalMs,                  // 周期；0 = 仅手动/规则触发
    NodePayloadSource Payload);

sealed record ResponseRule(
    MessageRef Trigger,
    BytePattern? Condition,          // 可选：payload 偏移+掩码+值
    NodeAction Action,
    int DelayMs);                    // 响应延迟（模拟真实设备节奏）

// ── NodeAction 判别联合（GBT27930 全流程推演后定稿，四种原语 + 逃生口）：
//    收 BRM 后置 CRM 辨识标志 = SetSignal；收 BRO 后开始发 CCS = StartMessage；
//    收 BST 后停发 CCS 并回 CST = StopMessage + SendMessage。
abstract record NodeAction;
sealed record SendMessageAction(MessageRef Ref, NodePayloadSource Payload) : NodeAction;
sealed record SetSignalAction(string MessageName, string SignalName, double Value) : NodeAction;  // 写 Runtime，下周期生效
sealed record StartMessageAction(MessageRef Ref) : NodeAction;   // 启动周期表中已定义消息的周期发送
sealed record StopMessageAction(MessageRef Ref) : NodeAction;    // 停止周期发送
sealed record ScriptAction(string ScriptRef) : NodeAction;       // 复杂逻辑逃生口（复制触发报文信号、闭环计算等）
// NodeMessage 增加 Enabled 初始态（bool，默认 true）——StartMessage 的配对语义：
// 周期表中 Enabled=false 的消息在节点 Start 时不发，等待规则 StartMessage 启动。

// ── INodeContext 完整签名（定死）——behavior 与宿主之间的唯一通道
interface INodeContext
{
    NodeIdentity Identity { get; }
    NodeRuntimeState Runtime { get; }
    // 发送经后端路由：J1939MessageRef → J1939TpLayer（>8B 走 BAM/RTS-CTS，≤8B 单帧直发）；
    // CanMessageRef → SendService 单帧（本期不实现，调用即 NotSupportedException）。
    void Send(MessageRef target, NodePayloadSource payload);
    // 后端过滤后的消息到达（J1939 后端 = J1939TpLayer.MessageReceived 按规则预过滤）。
    event Action<NodeMessageArrived>? MessageArrived;
    TimeProvider Clock { get; }      // 生产 TimeProvider.System；测试 FakeTimeProvider
}

sealed record NodeMessageArrived(MessageRef Ref, byte Sa, byte[] Payload, double TimestampSec);

// NodeRuntimeState：键为 (DBC 消息名, 信号名) 字符串对——DbcSignals payload 按名引用。
public sealed class NodeRuntimeState
{
    public void SetSignalValue(string messageName, string signalName, double value);
    public bool TryGetSignalValue(string messageName, string signalName, out double value);
}
```

- **J1939 后端职责**（不进通用核心）：`NodeIdentity` 携带 SA（充电机 `0x56` / BMS `0xF4`）、SA 冲突校验（同服务内唯一，冲突拒绝启动）、向 `J1939TpLayer` 注册/注销 `_localAddresses`；
- **扩展锚点 4——多通道**：`NodeIdentity.Channel` 现在即引入（可空），对齐 hil-core 多通道演进，避免将来"通道 1 演 BMS、通道 2 演充电桩"时改身份模型；
- **NodeHostService**（DI singleton）API 定死：

```csharp
public sealed class NodeHostService
{
    IReadOnlyList<SimulatedNode> Nodes { get; }
    Result<Unit> AddNode(NodeConfig config);            // SA 冲突 → Error（J1939 后端校验）

    Result<Unit> StartNode(string name);                // 幂等；未知名 → Error

public sealed record NodeActivity(

```

**线程模型（契约）**：`NodeHostService` 订阅 `J1939TpLayer.MessageReceived`（SDK 读线程触发）后**只入队不处理**——内部 `System.Threading.Channels` 有界队列（容量 256，满则丢弃最老 + LogWarning）+ 单 consumer 任务做规则匹配与响应发送；周期消息调度经 `TimeProvider` 定时器在 consumer 任务内结算。SDK 读线程零阻塞（满足 sink 契约）；
- **NodeConfigLibrary**：JSON 持久化到 `%APPDATA%\PeakCan.Host\nodes\`，atomic write（tmp+rename），仿 `SequenceLibrary`；文件后缀 **`*.node.json`**；schema 带 `version` 字段 + `JsonPolymorphic` 的 `kind` discriminator（库升级不炸）；随库附带 `gbt27930-bms.node.json` / `gbt27930-charger.node.json` 模板；
- **NodeSetupViewModel**：见 §10.2 UI 设计；
- Address Claim（PGN 60928）：节点级 bool 选项，默认 **false**（GBT27930 地址固定，发出可能干扰被测件）；
- **B3 不做**：多步协商/重试/超时告警等时序逻辑——扩展路径已由锚点 1 预留（`StateMachineBehavior` 作为 `INodeBehavior` 并列实现加入，不动节点类）；本期复杂逻辑经 `ScriptAction` 逃生口。

### 10.1 GBT27930 模拟充电机可行性推演（验收场景）

以"模拟充电机陪真实 BMS 跑完整充电流程"为验收场景，逐环节对照能力：

| GBT27930 环节（充电机侧） | 配置手段 | 覆盖 |
|---|---|---|
| 周期发 CHM（3B 单帧）、CRM（8B 单帧） | `NodeMessage` + `IntervalMs`（≤8B 经 `INodeContext.Send` 单帧直发） | ✅ B1 |
| 收 BRM（41B BAM 多帧）→ CRM 辨识标志位置位 | 规则：Trigger=BRM → `SetSignalAction(CRM, 辨识完成, 1)`；下周期 CRM 生效 | ✅ B1+B2 |
| 收 BCP（13B BAM）/ BRO → 开始发 CCS（8B，50ms） | CCS 在周期表中 `Enabled=false`；规则：Trigger=BRO → `StartMessageAction(CCS)` | ✅ B1+B2 |
| 周期发 CML（8B）、CCS；收 BCL/BCS/BSM（BAM 多帧）监视 | 周期表 + 规则监视 | ✅ B1+B2 |
| CCS 输出电压/电流跟随 BCL 需求（闭环） | 简单策略：规则复制需求值→`ScriptAction`（跨信号计算）；复杂控制（恒流恒压、斜坡）→ `ScriptAction` | ⚠️ 脚本逃生口 |
| 收 BST → 停发 CCS + 回 CST（4B） | 规则：Trigger=BST → `StopMessageAction(CCS)` + `SendMessageAction(CST)` | ✅ B2 |
| 结束发 CSD（8B） | 规则或手动触发 | ✅ B1+B2 |
| 严格按国标的阶段状态机（超时重试、错误码分支） | `StateMachineBehavior`（B3，本期不做）或 `ScriptAction` | ⚠️ 边界 |

**结论**：报文层（单帧 + BAM 多帧收发）100% 覆盖；流程推进用"ECA 规则链"（收 X → 停 A / 启 B / 置标志 C）可覆盖 GBT27930 主流程——因为国标的阶段切换本质上都可表达为该原语组合。真正的边界在**跨信号闭环计算**与**严格状态机语义**，两者由 `ScriptAction` 承接，B3 留给 `StateMachineBehavior`。模拟 BMS 侧同理（镜像配置，`gbt27930-bms.node.json` 模板即此）。

## 11. 数据流

**实时接收**：硬件 → `ICanChannel.FrameReceived` → `ChannelRouter` → `J1939TpSinkAdapter` → `J1939TpLayer.ProcessFrame` → `MessageReceived` → `NodeHostService`（规则匹配 → 触发节点响应发送）+ 实时重组显示。

**发送（手动/周期/节点）**：VM/Node → `J1939TpLayer.SendBamAsync / SendRtsCtsAsync` → `ISendService` → `ICanChannel.WriteAsync`（TP.CM/TP.DT 原始帧同样流经 Router → Trace/Record 可见，与 CANoe 一致）。

**回放分析**：ASC/BLF → `ITraceViewerService.LoadedFrames` → `J1939ReassemblyService`（离线模式）→ L2 视图行 + L3 虚拟帧 → 信号解码/图表/watch/AI 工具。

## 12. 错误处理

| 场景 | 行为 |
|---|---|
| 畸形 TP 帧 | `Decode` 抛 `ArgumentException` → sink adapter 窄捕获 → LogDebug 丢弃，接收路径不断 |
| 序号跳变 | 会话作废 + `SessionEvent(PacketLoss)`，后续 DT 丢弃直至新 TP.CM |
| 长度超限 | RTS/BAM 宣告 > `MaxPayloadBytes` → 拒绝建会话 + LogWarning |
| 会话表满 | LRU 驱逐最老会话 + `SessionEvent(Evicted)` |
| T1/T3/T4 超时 | 会话作废 / 发送状态机失败 + LogWarning |
| 发送 `WriteAsync` 失败 | 中止状态机，`Result.Error` 上报调用方，不重试 |
| 节点 SA 冲突 | `NodeHostService.Start` 拒绝 + 用户可读错误消息 |
| sink/handler 抛异常 | 锁外调用 + try/catch 隔离（同 IsoTpLayer），不污染重组状态 |

- RTS/CTS：发起方与接收方**对打**（两个 layer 实例经 loopback channel 互联，复用 `VirtualChannel`/`TraceDrivenChannel` 测试基建）：正常流、CTS 分段（maxPackets=2）、hold（maxPackets=0）、Abort、T1/T3/T4 超时（fake 时钟或短超时注入）；
- 会话驱逐、发送取消（`CancellationToken`）。

**App 单测**：

- `J1939TpSinkAdapter`：不抛异常契约、畸形帧不断流（对照 `IsoTpSinkAdapterTests`）；
- `J1939ReassemblyService`：构造含 6 包 BAM 的帧列表 → Complete/Truncated/PacketLoss 三态；
- `SimulatedNode`：周期调度、规则匹配（含 Condition）、SA 冲突拒绝、启停幂等、`SetSignalValue` → 下一周期 live 生效、JSON discriminator round-trip（含未知 `kind` 的容错策略）；
- `NodeConfigLibrary`：JSON round-trip、损坏文件 → 空库。

**集成验证**：

- 录制/构造一份含 GBT27930 BAM 流量的 ASC，经 Trace Viewer 端到端：L2 视图出现完整消息、L3 信号值与 DBC 定义一致；
- **Task 0 spike（先行）**：验证 `SignalDecoder.Decode` 对 >8 字节数据无 64-bit 截断（41 字节 BRM 用例）+ GBT27930 DBC 的 ID 惯例与 §9.3 匹配回退策略。若 spike 不通过，L3 方案降级为"L2 视图内嵌信号解码表"，spec 同步修订。

## 16. 接口契约通则（施工前必读）

1. **目录 ↔ 命名空间映射**：项目文件夹为 `src/PeakCan.Host.Core/`，但命名空间根是 `PeakCan.HIL.Core`（既有约定）。新增代码：`src/PeakCan.Host.Core/J1939/` → `namespace PeakCan.HIL.Core.J1939`；`src/PeakCan.Host.App/Services/J1939/` → `PeakCan.Host.App.Services.J1939`；`src/PeakCan.Host.App/Services/Nodes/` → `PeakCan.Host.App.Services.Nodes`。
2. **`Result<T>`/`Unit`**：复用 Core 现有类型（`ICanChannel.WriteAsync` 同款），不新建结果类型。
3. **事件线程通则**：凡协议层/服务层事件（`MessageReceived`、`SessionEvent`、`NodeHostService.Activity`），均在触发方线程同步引发；xmldoc 必须标注线程来源；UI 订阅方自行 marshal。
4. **位运算收敛**：J1939 ID 的组合/分解只允许经 `J1939Id`（构造 + `Compose`）；PGN 在 TP.CM payload 内的 3 字节小端编解码只允许在 `TpCmMessage` 内出现。
5. **时钟**：一切定时（BAM 间隔、T1/T3/T4、节点周期）经 `TimeProvider`；禁止 `Task.Delay`/`Timer` 直建——单测用 `FakeTimeProvider` 驱动。
6. **日志**：`[LoggerMessage]` source-gen；EventId 顺延 Core 现有号段（3001–3003 之后起 3101），App 层顺延现有号段，plan 阶段列编号表。
